## How to read this page

This page collects the cross-cutting traps; each area's dedicated page has the full model. Rows are grouped by area and ordered so that data-loss and security issues come first, correctness traps next, and ergonomics last. Columns:

| Column | Meaning |
| --- | --- |
| **Gotcha** | What bites you, with an inline severity label: `(high)`, `(medium)`, `(low)`, `(info)`. |
| **Impact** | What you observe (the symptom to search for). |
| **Where** | Source anchor, `file:line`, relative to the module root. |
| **Workaround / fix** | What to do about it, or why the behavior is deliberate. |

> **Warning:** several traps only appear on the **second** run: credential reuse, header-protection key persistence, output overwrite, and the obfuscation re-draw. A first run on an empty `output/` hides all of them.

> **Note:** not every row is a bug. Version gates, `{0,0}` disabling a key, the in-memory build phase, and `0750`/`0600` file modes are deliberate design decisions; each row says which.

## Credentials and data loss

Key material is recovered from the emitted configs, not from a state file. See [Credentials & Key Reuse](./credentials.md) for the full persistence model.

| Gotcha | Impact | Where | Workaround / fix |
| --- | --- | --- | --- |
| **The output tree is the credential store** `(high)` | There is no separate key store: the server key pair and the header-protection key come from `output/<server>/awg0.conf`, and each peer private key from `output/<peer>/awg0.conf`. Deleting `output/` or one peer directory silently rotates the missing material on the next run. | `credentials.go:52-105`, `pipeline.go:633-655` | Back up `output/` like a credential store; never delete individual peer directories. If a peer config is missing, the next run issues that peer a fresh key pair and PSK. |
| **The header-protection key is persisted only inside the emitted server config** `(high)` | Any run whose output has no 3.x key (`awg_version` `"2.0"`, or `header_protection: false`) drops it from the persisted state, so the next 3.1 run generates a new key. Every client still configured with the old key stops completing handshakes. Live-verified: 3.1 → 2.0 → 3.1 rotated the key. | `credentials.go:71`, `pipeline.go:76-81`, `e2e/awg31_e2e_test.go:152-181` | Keep a given fleet on one `awg_version`; after any version-changing run, re-import every client config. |
| **Losing the server config's `PublicKey` line permanently breaks every client config** `(high)` | `resolvePeerCredentials` reuses the persisted server key pair verbatim (private **and** public) with no re-derivation, unlike the client path. With no `PublicKey` line, the next run writes `PublicKey = ` (empty value, trailing space) into every client `[Peer]`, silently: exit 0, no finding, no error. Verified live. | `pipeline.go:389-398`, `pipeline.go:604`, `writer.go:14-16`, `writer.go:170` | Restore the line, or recover with `--full-reset` (or by deleting the output tree). Check the server config's `PublicKey` line after any hand-edit. |
| **A corrupt client `PrivateKey` panics `generate`** `(high)` — defect | The loader derives the public key defensively (`tryDerivePublicKey` swallows the panic), but the pipeline always re-derives with `DerivePublicKey`, which panics on invalid base64 or a length other than 32 bytes. Observed with `PrivateKey = not-a-valid-key`: `panic: crypto: invalid base64 private key: illegal base64 data at input byte 3`, exit 2. | `credentials.go:174-190`, `pipeline.go:422`, `keys.go:34-41` | Fix or remove the `PrivateKey` line in `output/<peer>/awg0.conf` before re-running. |
| **A corrupt `HeaderProtectionKey` blocks `generate` entirely** `(high)` | Any parse failure of the server config is fatal (`load server config for credentials: ...`), and the parser rejects a key that is not 44-char base64 of 32 bytes. There is no fallback to regeneration. | `credentials.go:56-59`, `parser.go:224-231` | Fix or delete the offending file. CLI `validate` reports the parse failure as `PSE001`; `HPK003` is library-only and fires only on an already-parsed in-memory config. |
| **`--full-reset` is all-or-nothing** `(high)` | It discards every persisted peer key pair, every PSK, and the header-protection key. Every previously distributed config stops working with the newly generated server config. | `pipeline.go:381-432`, `pipeline.go:675-680` | Treat it as a fleet-wide re-provisioning action, never a local refresh. Without it, keys are reused. |
| **A peer whose `#_Name` is missing from the server config rotates its keys every run** `(medium)` | `loadPeersFromServer` skips peers without a name, so no persisted entry exists and a fresh key pair plus PSK is generated. Renaming a manifest peer has the same effect because the name is the match key. | `credentials.go:112-114`, `pipeline.go:411-420` | Keep the `#_Name` metadata intact; renaming a peer is a credential rotation. |
| **The header-protection key is stored in plaintext in every config** `(high)` | `HeaderProtectionKey` is a normal (non-`#_`) INI key duplicated in the server and every client config, so anyone who can read a client config can decrypt header-protected headers. | `writer.go:115-117`, `credentials.go:71` | Treat client configs as secrets — they already contain private keys — and restrict access to `output/`. |
| **`vpn://` links embed private keys** `(high)` | `last_config.config` contains the verbatim client INI (private key, PSK) plus the same secrets as structured fields. A `.vpn` file is as sensitive as the client config itself. | `vpnlink.go:68`, `vpnlink.go:70-74`, `vpnlink.go:133-137` | Handle `.vpn` files like credentials; do not paste them into tickets or chat. |

## Reuse and reproducibility

`generate` reuses persisted credentials but re-resolves obfuscation parameters on every run. See [Credentials & Key Reuse](./credentials.md).

| Gotcha | Impact | Where | Workaround / fix |
| --- | --- | --- | --- |
| **Key reuse does not mean config stability** `(high)` | Reuse is asymmetric: only the peer key pairs, PSKs, and header-protection material persist. Every obfuscation field left `null` in the manifest is re-drawn from `crypto/rand` each run: S1-S4, H ranges, and Jc/Jmin/Jmax. Verified over six runs on the 3.1 fixture: keys stayed byte-identical while `Jmin` varied 311-995 and S values came back 31, 31, 21, 17, 22, 23. Previously distributed clients can no longer handshake after an unpinned regeneration. | `pipeline.go:42-103`, `pipeline.go:181-206`, `pipeline.go:320-345`, `pipeline.go:658-720` | Pin every S/H/J value in the manifest for byte-stable runs; otherwise re-import every client after each `generate`. |
| **`--peer <one>` leaves every other client on stale obfuscation** `(high)` | The server config is always rewritten with newly resolved S/H/J, while peers excluded by the filter keep configs from an earlier run. Those peers can no longer complete a handshake. | `pipeline.go:697-744`, `pipeline.go:181-236` | Regenerate all peers together (omit `--peer`) unless obfuscation is fully pinned. |
| **A filtered or dry run discards freshly generated keys** `(low)` | `--dry-run` computes keys in memory and writes nothing, so a later real run writes different keys. On a first run there is no output tree to reuse from, so the preview never matches the real run; there is no way to preview exact keys. | `pipeline.go:666-679`, `pipeline.go:745-761`, `internal/cli/generate.go:92-94` | Run a real `generate`, then inspect the files; use `--dry-run` only to check structure and sizes. |
| **I1-I5 are regenerated on every run** `(medium)` | CPS strings are not persisted or pinnable, so re-running produces different I-packet sizes in client configs even when keys are stable. Diffing outputs always shows I1-I5 churn. | `pipeline.go:571-578`, `cps.go:121-127` | Expected behavior; compare with CPS ignored, and re-import configs after regeneration. |

## Generation and I/O

The write phase is deliberately two-pass but not atomic. See [Output Format](./output-format.md) for the emitted file layout.

| Gotcha | Impact | Where | Workaround / fix |
| --- | --- | --- | --- |
| **`generate` is not atomic on disk** `(high)` | Every config is built in memory first, so a build failure writes nothing — but the write loop itself is plain `os.MkdirAll(0750)` plus `os.WriteFile(0600)` per file, with no temp file, rename, or rollback. An I/O failure or crash partway leaves earlier files updated and later ones stale. | `pipeline.go:745-765` | Re-run `generate` after any interruption instead of trusting a partially updated tree. Treat `output/` as regenerated, not hand-edited. |
| **`SaveServerConfig` is atomic, but `generate` never uses it** `(medium)` | The library exposes write-to-`.tmp`-plus-rename; the CLI pipeline bypasses it. Library consumers who call the helper directly get atomic single-file saves, CLI users do not. | `writer.go:181-195` | In library code, prefer `SaveServerConfig`; do not assume CLI-generated trees are crash-consistent. |
| **`generate` re-parses its own server config but ignores parse errors** `(medium)` | Findings are appended only when the generated config parses successfully, so a malformed generated config produces no error and no findings — failures surface only as a broken tunnel. Client configs are never re-parsed at all. | `pipeline.go:685-694` | Point `validate` at the generated file to close the gap; a clean `generate` is not proof the config is parseable. |
| **Findings from `generate` have no location** `(low)` | In-memory configs carry empty `Location.File`/`Location.Line`, so `Finding.OneLine()` renders a double space: `[WARNING TRL001]  (key=RandomTrailers): ...`. `validate` re-stamps the file path, which is why the same finding looks different in the two commands. | `pipeline.go:690-694`, `internal/cli/validate.go:84-90` | Do not parse the location column from `generate` findings; use `validate --output json` when you need structured locations. |
| **The output directory is never printed** `(low)` | The CLI prints relative paths and sizes only (`  server/awg0.conf (743 bytes)`), so the destination is implicit in `--output` (default `<project>/output`). A first run creates directories with mode `0750` and files with `0600`. | `internal/cli/generate.go:96-100`, `pipeline.go:750-760` | Compute the path yourself when scripting; remember the default is relative to the project directory. |
| **`--dry-run` still reports byte counts** `(low)` | The flag computes and prints the full file list including sizes and only skips the write step; the leading `Dry run — no files written` line is the only signal. | `internal/cli/generate.go:92-100`, `pipeline.go:745` | Verify the marker, not the presence of output lines, when scripting dry runs. |
| **Client configs always emit `DNS = ` and `PersistentKeepalive = 0`** `(low)` | The client writer writes `DNS = ` with an empty value when `network.dns` is unset and always writes `PersistentKeepalive = 0` when the peer sets no keepalive; the server writer omits both. Valid, but easy to mistake for a rendering bug. | `writer.go:131-140`, `writer.go:174-179`, `pipeline.go:586-615` | None — this is the intended shape; the server config never carries either line. |
| **`#_` metadata comments are load-bearing** `(low)` | The writer appends `#_EndpointV4`, `#_EndpointV6`, `#_ClientToClient`, `#_TunName`, `#_MainIface` in `[Interface]` and `#_Name`, `#_PrivateKey`, `#_GenKeyTime` in `[Peer]`. They are parsed back for identity and credential reuse but are not engine keys. | `writer.go:52-89`, `credentials.go:108-130` | Do not strip them in post-processing: dropping them loses credential reuse and peer names. |
| **The pipeline never produces `#_EndpointV4`, `#_EndpointV6`, peer `#_PrivateKey`, or `#_GenKeyTime`** `(medium)` | The writer and parser support all four, but `buildServerConfig` does not populate the corresponding fields. Documentation examples showing these lines describe hand-written configs, not generated output. | `writer.go:50-55`, `writer.go:77-79`, `writer.go:85-87`, `pipeline.go:453-463`, `pipeline.go:515-524` | Do not build tooling that expects these metadata lines in generated files. |
| **`awg setconf` cannot apply the whole generated server config** `(medium)` | `Address`, `MTU`, `DNS`, `PublicKey`, `PostUp`, `PostDown`, and `PersistentKeepalive` are wg-quick-style keys, not setconf keys; the e2e harness strips exactly those before applying a generated config to a live interface. | `e2e/harness_test.go:44-52`, `e2e/harness_test.go:230-270` | Apply the crypto/obfuscation keys plus `ListenPort` with `awg setconf`; configure the address, MTU, and routes with `ip`. |

## Version gates, MTU, and runtime

Manifest fields are gated by `obfuscation.awg_version`; emitted keys are gated by the resolved version. See [Transport Protection (AWG 3.x)](./transport-protection.md).

> **Warning:** omitting `network.mtu` is a defect, not a design decision. Until it is fixed, always set `network.mtu` explicitly (1280 is the default).

| Gotcha | Impact | Where | Workaround / fix |
| --- | --- | --- | --- |
| **An omitted `network.mtu` collapses every client I-packet to `<t>`** `(high)` — defect | The client INI still says `MTU = 1280` (the default is applied at `pipeline.go:580-582`), but `GenerateCPS` is called first with the raw manifest MTU (`0`) at `pipeline.go:577`, so `calculateMaxISize` goes negative and I1-I5 all fall back to the 4-byte bare timestamp. Verified live: a manifest with no `network` section emitted `MTU = 1280` with `I1`-`I5` all `<t>`, losing the protocol mimicry. | `pipeline.go:577-584`, `cps.go:156-186` | Set `network.mtu` explicitly in every manifest (the default already is 1280). The candidate fix is to apply the default before the `GenerateCPS` call. |
| **Manifest fields for a newer generation are hard errors** `(high)` | `header_protection`, `content_padding`, `rekey_after_time`, `rekey_timeout`, `reject_after_time`, `keepalive_timeout`, and `max_handshake_attempts` below 3.0 — and `random_trailers`/`disable_cookies` below 3.1 — fail with `obfuscation.<field> requires awg_version <version> or later (got "<got>")`. Fields are not silently ignored. | `pipeline.go:105-142` | Raise `awg_version`, or remove the field. Match the manifest to the oldest engine you deploy. |
| **`header_protection: false` under `awg_version` 2.0 is still an error** `(medium)` | The field is version-gated by presence, not by value: setting it at all while `awg_version` is `"2.0"` fails with `obfuscation.header_protection requires awg_version 3.0 or later (got "2.0")`. | `pipeline.go:105-133` | Raise `awg_version` or remove the field. The 3.x behavior of `header_protection: false` is covered in [Transport protection](#transport-protection). |
| **Older engine builds are documented to reject the nine 3.x keys** `(medium)` | amneziawg-tools aborts config loading on unknown INI keys with `Line unrecognized`; the writer therefore gates emission on `ServerObfuscationConfig.Version` and emits nothing below AWG 3.0. No in-repo test runs a pre-3.1 engine, so this rests on the code comments plus the engine's own error string — verify against the runtime you actually deploy. | `version.go:5-8`, `writer.go:107-114`, `pipeline.go:101-103` | Align the target `awg_version` with the oldest engine in the fleet. |
| **The runtime must be 3.x for 3.1 configs to work** `(medium)` | The transport-protection keys are engine features: the shipped image is pinned to `amneziavpn/amneziawg-go:3.1.20260828`, and a 2.0-era userspace build or a kernel implementation without the transport-protection layer cannot use them. | `Dockerfile:19`, `e2e/main_test.go:20-27`, `e2e/main_test.go:139-149` | Run an AmneziaWG 3.1 userspace engine aligned with the manifest's `awg_version`. |
| **A zero-value `Version` on a hand-built `ServerObfuscationConfig` drops the whole transport block** `(medium)` | `writeTransportProtectionKeys` returns immediately when `Version < AWG30`, and the zero `AWGVersion` is `0`. Library consumers that copy a config around without setting `Version` get a config that parses as legacy 2.0. | `writer.go:112`, `version.go:10-25` | Set `Version` explicitly in library-built configs. |
| **2.0, 3.0, and 3.1 produce different shapes for the same manifest** `(medium)` | Under `"3.0"` the H ranges stay `1-1`..`4-4` and the HP key, content padding, and timer ranges are emitted, but `RandomTrailers`/`DisableCookies` are absent; under `"2.0"` none of the nine keys appear. The S draws also differ: uniform S is used only under random trailers (3.1). | `pipeline.go:144-161`, `pipeline.go:181-206`, `writer.go:111-129` | Diff configs per target version; do not assume one manifest yields one shape across versions. |
| **CLI error wrapping hides the raw message prefix** `(low)` | An invalid `awg_version` such as `"3"` fails with `unsupported awg_version "3" (expected "2.0", "3.0", or "3.1")`, and the CLI prefixes it with `generating configs: resolve obfuscation: `. S-floor and version-gate errors get the same prefix. | `version.go:40`, `pipeline.go:675-679`, `internal/cli/generate.go:88-90` | Match scripts on the inner message, not the start of the line. |

## Transport protection

Header protection, content padding, timers, and the 3.1 booleans. See [Transport Protection (AWG 3.x)](./transport-protection.md) for the full model.

| Gotcha | Impact | Where | Workaround / fix |
| --- | --- | --- | --- |
| **S1-S4 must be at least 12 under header protection** `(high)` | The ChaCha20 nonce is built from the first 12 bytes of the S-prefix, so a pinned value below 12 aborts generation with `header protection requires S1-S4 >= 12 (got S<n>=<value>)` — exit 1, nothing written. `validate` reports the same condition as `HPK001`, with the message `header protection requires S1-S4 >= 12 (got S1=..., S2=..., S3=..., S4=...)`. The check is skipped when header protection is off. | `pipeline.go:163-174`, `validation.go:297-314` | Pin S1-S4 at 12 or above whenever a header-protection key is in play; below 12 is legal only under 2.0 or `header_protection: false`. |
| **Uniform S is generated only when all four S values are unset** `(medium)` | The uniform path is selected by `randomTrailers && S1 == nil && S2 == nil && S3 == nil && S4 == nil`. Pinning even one S switches the other three to independent draws, and validate then emits `TRL001` (`RandomTrailers is enabled while S1..S4 differ; the AWG 3.1 reference recommends equal S values to avoid packet-type misclassification`) as a warning, not an error. | `pipeline.go:59-69`, `validation.go:336-355` | Keep S1-S4 equal when `random_trailers` is on — the AWG 3.1 reference recommendation — or set `random_trailers: false`. |
| **Four presets always emit `TRL001`** `(medium)` | `home-balanced` (30/35/20/12), `mobile-aggressive` (60/60/50/24), `stealth-paranoid` (30/24/20/32), and `standard-1420` (32/28/20/16) pin unequal S with `RandomTrailers` enabled, so every `generate` prints `Warnings: 1` for them. | `presets.go:73-223`, `presets_test.go:236-259` | Expected for those presets; equalize S or disable random trailers if you want a clean run. See [Presets](./presets.md). |
| **Pinned S values are never re-drawn** `(high)` | An explicit S is used verbatim; only the ≥12 floor is enforced, so a hand-picked set can violate the padded-size distinctness invariant and surface only later through validation or analysis findings. | `pipeline.go:163-177`, `validation.go:78-129` | Prefer unpinned S (let the generator draw) or verify pinned sets with `validate` and `analyze`. |
| **`H = 1..4` under header protection is a pipeline shortcut, not a rule** `(medium)` | `standardHeaderRanges` (`1-1`, `2-2`, `3-3`, `4-4`) is used only when header protection is active **and** all four H fields are `null`. One explicit H field makes the other three draw large random ranges, and the explicit value is used verbatim. | `pipeline.go:207-245` | Do not assume pinning `h1` implies the rest of the reference set; pin all four or none. |
| **Overlapping H ranges are not detected by amnezigo validation** `(medium)` | Validation only checks `HDR001` (WG type-ids, suppressed under header protection) and `HDR002` (`Max < Min`). A partial explicit H set can overlap freshly generated ranges, and the engine rejects it only at `awg setconf` time with `headers must not overlap`. | `pipeline.go:207-236`, `validation.go:263-296`, `e2e/awg31_e2e_test.go:302-331` | Verify mixed explicit/generated H sets against a real engine before distributing configs. |
| **`header_protection: false` does not disable the other 3.x keys** `(medium)` | It only removes the `HeaderProtectionKey` line; the six uint16 ranges and the 3.1 booleans are still emitted, and the H ranges switch from `1-1`..`4-4` to large generated ranges, which `RISK007` will then flag. | `writer.go:111-128`, `pipeline_test.go:1010-1049` | Do not treat `header_protection: false` as "plain 3.1"; it is a half-disabled state. |
| **A missing bound in a `U16Range` means DISABLED, not "use the default"** `(medium)` | `{"min": 0}` decodes to `{0,0}`, which is the disabled/omitted state, and `{"min": 0, "max": 5}` is a hard error: `obfuscation.<field>: bounds must both be zero or both non-zero (got 0-5)`. `TRM001` catches half-zero ranges in `validate`. | `types.go:14-39`, `pipeline.go:302-318`, `validation.go:357-397` | Omit the key to keep the engine default; use a fully non-zero range to set one. `{0,0}` cannot express "start at zero". |
| **`TRM001` reports only the first structural problem per range** `(low)` | An inverted range is checked first and the loop `continue`s, so a range that is both inverted and mixed-zero is reported once; `{0,0}` never produces a finding by design. | `validation.go:357-397` | Fix the reported problem and re-run; do not expect a complete list in one pass. |
| **H ranges are always written as two-part `Min-Max`** `(low)` | The writer emits `H1 = 1-1`; the parser only accepts the two-part form, so a bare `H1 = 7` in a hand-edited config parses to `HeaderRange{}` silently. Only the 3.x `U16Range` keys collapse to the short `N` form. | `writer.go:42-45`, `parser.go:320-331` | Write H values as `Min-Max` when editing configs by hand. |
| **The header-cipher nonce is 12 bytes, not S bytes** `(medium)` | The HPK001 detail says the ChaCha20 nonce is the first 12 bytes of the packet; a generator comment saying "the first S bytes" is loose wording. This is exactly why S1-S4 ≥ 12 is required. | `generator.go:23-28`, `validation.go:312-314` | Use the 12-byte rule when reasoning about the floor. |
| **S4 caps at 32 while S1-S3 cap at 64** `(medium)` | `GenerateSPrefixes` draws S1-S3 in `[minS, 65)` and S4 in `[minS, 33)`. `ValidatePacketSizes` is generic and accepts an out-of-range S4 (for example 116) as long as padded sizes differ. | `generator.go:11-12`, `generator.go:35-52` | Keep pinned S4 at 32 or below; do not rely on validation to catch an oversized one. |
| **Padded-size distinctness has six pairs, not one** `(medium)` | The invariant is pairwise distinctness of `S1+148`, `S2+92`, `S3+64`, and `S4+32`. Older guidance that mentions only `S1+56 != S2` understates the check and can mislead you into thinking one comparison is enough. | `generator.go:82-93`, `generator_test.go:29-32` | Let the generator draw the set, or check all six pairs. |
| **`RandomTrailers = true` is not valid engine input** `(low)` | The parser accepts only case-insensitive `on`/`1`/`off`/`0` and rejects anything else with `expected on/off/0/1, got "true"`. The writer only ever emits `on`/`off`. | `parser.go:354-365`, `writer.go:91-96` | Use `on`/`off` in hand-edited configs. |

## Obfuscation and CPS

The CPS grammar and the S/H/J constraints are covered in depth in [Obfuscation](./obfuscation.md).

| Gotcha | Impact | Where | Workaround / fix |
| --- | --- | --- | --- |
| **`<c>` is a kernel-module-only tag that userspace engines reject** `(high)` | `BuildCPSTag("c", ...)` returns an empty string — the same sentinel as any unknown tag — and `CPSLength` counts it (like any unknown tag) as 0 bytes, so size accounting cannot catch it. The tag is recognised only by `amneziawg-linux-kernel-module`; amneziawg-go and every AmneziaVPN client reject it with `unknown tag`, and a raw literal `<c>` in a config file is flagged as `CPS001`. | `cps.go:80-111`, `cps.go:236-266`, `parser.go:85-101` | Do not use `<c>` in configs for userspace engines — the ones amnezigo targets and the only ones the pinned image ships; use `<rc>`/`<rd>` for random content. |
| **`<t>` is 4 bytes, not 8** `(medium)` | The timestamp tag is a `uint32` big-endian value. The old standalone guide claimed 8 bytes; at most one `<t>` per interval. | `cps.go:17-19`, `cps_test.go:100-110`, `cps_test.go:226-270` | Size intervals with 4 bytes per `<t>`. |
| **`<rc>` draws letters only** `(medium)` | The alphabet is the 52 ASCII letters `[a-zA-Z]`, not the commonly cited `[a-zA-Z0-9]`; there is no alphanumeric tag. Mixed fields need concatenation, for example `<rc 4><rd 2>`. | `cps.go:31-46`, `cps_test.go:31-77` | Use `<rd>` for digits and `<rc>` for letters, combined for mixed content. |
| **`<d>` contributes 0 bytes and needs AWG 2.0 userspace** `(medium)` | `<d>` is a runtime passthrough expanded by the userspace engine; the legacy `amneziawg-linux-kernel-module` rejects it (`unknown tag`). Random mode never emits `<d>` because a standalone random interval has no earlier interval to source the passthrough from. | `cps.go:56-66`, `cps.go:270-330`, `quic.go:38-45` | Use an AmneziaWG userspace engine; avoid `<d>` on kernel-module deployments (the kernel module rejects it), and remember `<c>` is the reverse — kernel-only — so neither tag is portable. |
| **Unknown or malformed tags silently count 0 bytes** `(medium)` | Unsupported tags contribute nothing to `calculateCPSLength`, and numeric parse failures inside a tag become 0 because the `strconv.Atoi` error is ignored. A typo shrinks the interval instead of failing validation. | `cps.go:227-264` | Check rendered sizes with `analyze`; do not rely on length arithmetic to catch typos. |
| **Explicit junk values skip collision checking at generation time** `(medium)` | `fillMissingJunk` short-circuits when Jc, Jmin, and Jmax are all explicit and copies them without checking the padded/raw forbidden set. The violation is only reported later by `validate` as `PSC002`. | `pipeline.go:320-326`, `validation.go:78-129` | Run `validate` after pinning J values; keep the range clear of the padded and raw WireGuard sizes. |
| **An explicit `"s1": 0` or `"jc": 0` is replaced** `(medium)` | `fillMissingSPrefixes` keeps only non-zero S values, so pinning S to 0 asks for a generated one. `fillMissingJunk` retries until `Jc != 0`. | `pipeline.go:320-345`, `pipeline.go:363-369` | There is no way to pin a zero S or Jc; omit the field instead. |
| **Generator retry exhaustion panics** `(medium)` | `GenerateSPrefixes`, `GenerateHeaderRanges`, `GenerateConfig`, and `GenerateServerConfig` panic after their 1000-attempt budgets, including `failed to generate non-colliding junk range after 1000 attempts`. | `generator.go:35-73`, `generator.go:137-162`, `generator.go:194-283` | Give the generator room (wider ranges, fewer pinned constraints) so retries do not exhaust; treat a panic here as a manifest problem. |
| **`obfuscation.protocol` is dead configuration** `(medium)` | The pipeline never reads the manifest's top-level `obfuscation.protocol`. Only `peers.<name>.protocol` selects the CPS template, and it defaults to `quic`. | `manifest.go:39`, `pipeline.go:507-510` | Set `protocol` per client peer; the top-level field is informational at best. |
| **Unknown protocol names still produce a plausible shape** `(medium)` | Only the exact value `random` takes the random-tag path. Any other string — including a typo — goes to the named-template path, whose default branch picks one of the six named templates at random. `analyze` and `generate` do not reject the name. | `cps.go:121-127`, `protocols.go:36-61` | Spell protocol names exactly; if the shape looks wrong, check for a typo first. |
| **SIP byte budgets in comments are approximate** `(low)` | `sip.go`'s comment claims roughly 360/240/170/120 bytes for I1-I4; measured rendered lengths are 312/203/140/87. RTP's commented budget does match. | `sip.go:49-55`, `rtp.go:40-49` | Measure with `analyze` instead of quoting the comment. |

## Manifest and loader

Loader and manifest semantics. See [Manifest Reference](./manifest-reference.md) and [Jsonnet](./jsonnet.md).

| Gotcha | Impact | Where | Workaround / fix |
| --- | --- | --- | --- |
| **`version` must be exactly 1** `(medium)` | `{}` decodes to version 0 and fails with `missing or zero version field`; any other value fails with `unsupported schema version N (expected 1)`. Jsonnet manifests must therefore emit `version: 1` in their output object. | `loader.go:120-133` | Always include `"version": 1` at the top level. |
| **`Manifest.Version` is only validated by the loaders** `(low)` | Library callers can construct a `Manifest` with `Version: 0` and `Generate` accepts it; the schema check lives in `validateManifestVersion` inside the JSON/Jsonnet loader. | `loader.go:120-133`, `pipeline.go:658-765` | Validate manifest files through the loader when version correctness matters. |
| **One stray `listen_port` turns a client into a second server** `(medium)` | A peer is a server whenever `endpoint` is non-empty **and** `listen_port` is non-zero, regardless of intent. A client that sets both makes the manifest contain two servers and `generate` fails with `exactly one server peer required, found 2` — no files at all. | `manifest.go:129-134`, `pipeline.go:661-664` | Set `listen_port` only on the server peer. |
| **Jsonnet wins over JSON** `(medium)` | Whenever `.amnezigo.jsonnet` exists, it is evaluated and `amnezigo.json` is silently ignored — a stale Jsonnet file shadows an edited JSON manifest. | `loader.go:26-46` | Delete or rename the stale file when switching formats. |
| **`--jpath` replaces `<project>/lib` and is CWD-relative** `(medium)` | `resolveJpath` returns the supplied list verbatim when it is non-empty: the implicit `<project>/lib` search path is used only with no `--jpath`. Relative `--jpath` values also resolve against the process CWD, not the manifest directory. | `loader.go:59-66`, go-jsonnet `imports.go:287-292` | Always include `<project>/lib` in `--jpath` if you rely on it, and use absolute paths in scripts. |
| **Duplicate imports resolve from the LAST `--jpath` directory** `(low)` | go-jsonnet's `FileImporter` iterates JPaths in reverse order, so when two directories contain the same filename, the last one on the command line wins. | go-jsonnet `imports.go:287-292` | Put an override directory last; put the base library first. |
| **No Jsonnet library ships with amnezigo** `(medium)` | There is no committed `lib/` directory and no `presets.libsonnet`; the importable `lib/` path is a user convention. Presets live in Go, so a manifest cannot import one and must hardcode the numbers. | `loader.go:59-66`, `presets.go:73-243` | Vendor your own library files; copy preset values manually. |
| **Presets are copy-by-value only** `(medium)` | There is no `preset` manifest field and no `--preset` flag; `GetPreset`/`ListPresets` have no non-test callers. Copying a preset also means copying its MTU and `DefaultProtocol` by hand, because `ToServerObfuscation` drops them. | `presets.go:223-242`, `manifest.go:16-18` | Copy the values into `obfuscation.*` and set `network.mtu` and per-peer `protocol` yourself. See [Presets](./presets.md). |
| **Jsonnet has no external variables, TLAs, or sandboxing** `(medium)` | Only a file importer is installed, so `std.extVar`/`std.native` fail with `Undefined external variable` and there are no `--ext-str`/`--tla-str` flags. Imports can traverse `../` or read absolute paths — `--jpath` is not an isolation mechanism. | `loader.go:108-117`, go-jsonnet `imports.go:227-232` | Pass parameters by generating Jsonnet files; do not run untrusted Jsonnet. |
| **`.jsonnet` detection is a case-sensitive suffix check** `(low)` | `LoadManifestFromFile` routes on `strings.HasSuffix(path, ".jsonnet")`, so `Manifest.Jsonnet` or `x.jsonnet.bak` is parsed as JSON and fails. `LoadManifest` only ever looks for the exact names `.amnezigo.jsonnet` and `amnezigo.json`. | `loader.go:13-16`, `loader.go:50` | Use exact filenames; pass explicit paths with the correct extension. |
| **Neither the loader nor the pipeline validates peer addresses or names** `(medium)` | Jsonnet comprehensions can easily emit duplicate addresses or colliding names; nothing rejects them before configs are written, so mistakes surface only at tunnel setup. | `loader.go:68-105`, `pipeline.go:721-744` | Diff the generated `Address` and peer names yourself. |
| **Client-only fields are silently ignored** `(medium)` | On a client peer, `tun_name`, `main_iface`, `endpoint`, `listen_port`, and `display_name` have no effect: client configs take the endpoint from the server peer and never carry the other fields. `display_name` appears only in `vpn://` links. | `pipeline.go:453-484`, `pipeline.go:594-613`, `manifest.go:74`, `vpnlink.go:256` | Set interface fields on the server peer only. |
| **A server peer's `keepalive` field is ignored** `(low)` | `PersistentKeepalive` is populated only from a client peer's `keepalive`; the same field on the server peer has no effect. | `pipeline.go:608-613`, `manifest.go:67` | Set `keepalive` per client peer. |
| **`#_ClientToClient = yes` silently means false** `(low)` | The parser compares the raw value to the string `"true"`, so `yes`, `1`, or `True` yields false. The writer always emits lowercase `true`/`false`. | `parser.go:147-148`, `writer.go:56` | Use `true`/`false` exactly when hand-editing. |

## Validation and analysis

Finding codes and machine output are documented in [Validation & Analysis](./validation.md).

| Gotcha | Impact | Where | Workaround / fix |
| --- | --- | --- | --- |
| **`validate` always strict-parses and does not know client from server** `(medium)` | `ParseServerConfigWithOptions` is called with `Strict: true` unconditionally, so client-only keys (`I1`-`I5`, `Endpoint`, `PersistentKeepalive`) become `KEY001` warnings and the missing `ListenPort` becomes an `FLD001` error. Verified live on a generated client config: 1 error and 6 warnings with the default quic template (named templates define no `I5`), 7 warnings when all five I-keys are present (for example `--protocol random`), exit 1 — even though the file is valid for the engine. | `internal/cli/validate.go:61-62`, `parser.go:50-71` | Validate server configs; treat `validate` on a client config as expected to fail. |
| **`validate` exits through `os.Exit`, not cobra** `(medium)` | A failed lint calls `exitFn(1)` inside the command, so no usage text is printed and deferred cleanup does not run. CLI-level failures (unreadable file, unknown `--output`) return a cobra error instead, which prints the usage block and then `Error: ...` a second time from `Execute`. | `internal/cli/validate.go:21-23`, `internal/cli/validate.go:111-120`, `internal/cli/cli.go:36-41` | Script on exit codes and stdout findings; expect doubled `Error:` lines for usage-level failures. |
| **`analyze` always exits 0 on findings** `(medium)` | Analysis findings are informational, so the command exits 0 even with `RISK` warnings and errors in the report. Only a config-load failure or an invalid `--output` value makes it exit 1. | `internal/cli/analyze.go:24-29`, `internal/cli/analyze.go:68-101` | Gate CI on parsed `--output json`, not on the exit status. |
| **`analyze --seed` does not make output reproducible** `(medium)` | The CLI builds a seeded generator and assigns it to `AnalyzeOptions.Rand`, but no code path reads that field — I-packet generation uses `crypto/rand`. Verified live: two runs with `--seed 42 --samples 5` produced different distributions, despite the help text. | `internal/cli/analyze.go:84-87`, `analysis.go:129-139`, `analysis.go:260-320` | Do not rely on `--seed` for repeatable reports; compare distributions, not exact numbers. |
| **`analyze` profiles regenerated I-packets, not the stored I1-I5** `(medium)` | `Analyze` calls `GenerateCPS` with an empty forbidden set and its own protocol, so the snapshot and distribution are fresh samples — not the config file's actual I1-I5 values. The report itself warns: `Note: I-packet sizes are freshly generated from config parameters and may differ on each run.` | `analysis.go:275-284`, `generator.go:185-190`, `analysis.go:156-160` | Read I1-I5 from the config itself when exact values matter. |
| **`generate` defaults to `quic`; `analyze` defaults to `random`** `(medium)` | The same config is described with different I-packet shapes unless you pass `--protocol` explicitly: the pipeline falls back to `ProtocolQUIC`, while `analyze` defaults its flag to `random`. | `pipeline.go:570-574`, `internal/cli/analyze.go:52-53` | Pass the same `--protocol` to both commands. |
| **Structural parse failures surface as `PSE001`, not as findings** `(medium)` | Malformed structures (invalid `HeaderProtectionKey`, a bad range value, a bad boolean, a structurally invalid H range) abort parsing and surface as a single `PSE001` finding. Semantic problems (`HPK001`/`HPK003`/`TRL001`/`TRM001`/`PSC*`) are findings on an otherwise parsed config. | `internal/cli/validate.go:56-95`, `parser.go:207-317` | Fix structural errors first; expect the semantic findings on the next run. |
| **`HDR001` is suppressed whenever a header-protection key is present** `(medium)` | WG type-ids in H ranges are rejected only without a key; under header protection the reference `1-1`..`4-4` set is expected. Overlap between H ranges is not a validator rule at all — the engine rejects it with `headers must not overlap`. | `validation.go:263-295`, `e2e/awg31_e2e_test.go:301-329` | Verify header-protected H ranges against a real engine. |
| **`PSC003` is unreachable from `ValidateServerConfig`** `(low)` | `validateSPrefixes` passes a nil `iPacketSizes` slice, so the CLI can never report an I-packet collision; `PSC003` is library-only. | `validation.go:245-249`, `validation_test.go:718-726` | Do not wait for `PSC003` in CLI output; check I-packet sizes with the library if needed. |
| **`JNK001` can be emitted twice** `(low)` | `validateSPrefixes` (via `ErrEmptyJunkRange`) and `validateJunkRange` both fire when `Jmin > Jmax`, so `ValidateServerConfig` returns two findings for the same defect. | `validation.go:212-217`, `validation.go:245-261`, `validation.go:410-419` | Deduplicate by code if you aggregate findings. |
| **`RISK004`/`RISK005` skip equal values** `(medium)` | Both require `0 < diff < 5`. Two identical padded sizes produce no `RISK004`, and a padded size exactly equal to a raw WireGuard size (for example `stealth-paranoid` S4=32 → 64) produces no `RISK005`. | `analysis.go:429-474` | Treat a clean `RISK004`/`RISK005` section as "no near-misses in the band", not "no collisions". |
| **`RISK007` fires below a 1,000,000-wide H range and is skipped under header protection** `(low)` | `lan-conservative` H1 has width 999,991 and trips it; the check is suppressed entirely when header protection is on. | `analysis.go:26`, `analysis.go:493-519`, `presets.go:85` | Interpret `RISK007` in the context of the header-protection state. |
| **INI parsing is agnostic to key version** `(low)` | The parser recognises all nine 3.x keys regardless of the config's target engine (INI files carry no version), so `validate` accepts a 3.1 key set that a 2.0 engine would reject. | `parser.go:47-63` | Rely on the runtime version, not on `validate`, for engine compatibility. |
| **`analyze --config` defaults to `awg0.conf` in the CWD** `(medium)` | The command reads `awg0.conf` relative to the current directory by default, so a clean checkout fails with a file-not-found error unless you point at the generated path. | `internal/cli/analyze.go:62` | Pass `--config output/<server>/awg0.conf` explicitly. |

## CLI

Flag-level traps. Exact flags and defaults are in the [CLI Reference](./cli-reference.md).

| Gotcha | Impact | Where | Workaround / fix |
| --- | --- | --- | --- |
| **`--output` means two different things** `(medium)` | For `generate` it is an output directory; for `validate` and `analyze` it is an output format (`text` or `json`). Scripts that share a flag variable between commands break. | `internal/cli/generate.go:41`, `internal/cli/validate.go:47`, `internal/cli/analyze.go:56` | Keep separate variables per command; read the flag's help text. |
| **`--peer` filters clients only, silently** `(medium)` | The server config is always rebuilt and counted, and a `--peer` value that matches no manifest peer is ignored without a warning — verified live: `--peer nobody` printed `Generated 1 config(s):` and exited 0. Credential resolution still loads every persisted peer. | `pipeline.go:697-744`, `internal/cli/generate.go:44` | Verify peer names against the manifest before relying on `--peer`. |
| **Bare `amnezigo` prints help and exits 0** `(low)` | The root command has no `RunE`, so cobra prints help and returns success; an unknown subcommand prints `Error: unknown command ...` twice and exits 1. Verified live. | `internal/cli/cli.go:21-42` | Assert on output, not on the exit code of a bare invocation, in smoke tests. |
| **`--vpn-links` writes an extra file per client** `(low)` | The flag appends `<peer>/amnezigo.vpn` (a text file containing one `vpn://` link) for every client peer, which shows up in the generated count and in the output tree. The link is importable by the AmneziaVPN app, not by the standalone AmneziaWG app. | `vpnlink.go:15-21`, `vpnlink.go:248-265`, `internal/cli/generate.go:46-49` | Expect the extra file; delete it if you do not use the links. See [VPN Import Links](./vpn-links.md). |
| **`vpn://` 3.x fields are inside the obfuscation-enabled branch** `(medium)` | `applyTransportProtectionFields` runs only when the client INI contains `Jc`; a `Jc`-less config loses `HeaderProtectionKey` and the other eight 3.x keys from `last_config`. The mapping is comment-documented but not pinned by a test, and no unit test references `HeaderProtectionKey` in `vpnlink_test.go`. | `vpnlink.go:129-130`, `vpnlink.go:154-174`, `vpnlink.go:211-229` | Verify generated links against the AmneziaVPN app before relying on 3.x fields. |
| **`vpn://` `allowed_ips` can be null** `(medium)` | The field has no `omitempty` and is built by splitting the INI `AllowedIPs` value, so a client INI without that key serializes `"allowed_ips": null` — the `JSONException` → error 1000 failure mode the encoder comments warn about. | `vpnlink.go:74`, `vpnlink.go:122-127` | Do not strip `AllowedIPs` from a client INI before generating links. |
| **Envelope `port` is a string; `last_config.port` is a number** `(low)` | `awg.port` is `strconv.Itoa(port)` while `last_config.port` is an int; a consumer must not assume one type across both. | `vpnlink.go:45`, `vpnlink.go:102` | Type-switch on the field's location when parsing links. |

## Build, release, and testing

Packaging and test-harness traps. Install instructions live in [Installation](./installation.md).

| Gotcha | Impact | Where | Workaround / fix |
| --- | --- | --- | --- |
| **Release matrix and container images are amd64 only** `(medium)` | GoReleaser builds `linux`/`darwin` on `amd64` only, the container image publishes `linux/amd64` only, and the runtime base image is amd64-only, so there are no arm64 artifacts. | `.goreleaser.yaml:25-26`, `.goreleaser.yaml:60-61`, `Dockerfile:19` | Apple Silicon users need `--platform linux/amd64` for images or a source build for the binary. |
| **The published image has no default user** `(medium)` | There is deliberately no `USER` directive: the CLI reads and writes configs in the mounted working directory. Runs without `--user` produce root-owned output files. | `cmd/amnezigo/Dockerfile:1-27`, `Dockerfile:20-26` | Pass `--user $(id -u):$(id -g)` on every `docker run`. |
| **GoReleaser re-publishes assets when a commit carries two tags** `(medium)` | Promoting an `-rc.N` to a final release on the same commit makes GoReleaser resolve the annotated RC tag first, so every asset upload fails with `422 already_exists`. | `.github/workflows/release.yml:46-53` | The workflow pins `GORELEASER_CURRENT_TAG` to the pushed tag; keep that pin when editing the release workflow. |
| **`NOTICE` and `licenses/` are generated and CI-enforced** `(medium)` | `hack/noticegen` resolves the module graph for both release targets and rewrites `NOTICE` plus `licenses/<module>/*`; the CI licenses job fails when the checked-in copies are stale. | `hack/noticegen/main.go`, `.github/workflows/ci.yml:92-103` | After any dependency bump, run `go run ./hack/noticegen` with a warm module cache and commit the result. |
| **The e2e suite self-skips without Docker or `/dev/net/tun`** `(medium)` | The suite probes `docker info` and a throwaway container able to `ls /dev/net/tun`; without either, tests skip instead of failing. A broken CLI or image build does fail, but a green local run does not prove the container tests executed. | `e2e/main_test.go:44-135` | Check for skips in the output, and run the suite in an environment with Docker plus TUN when validating the image. |
| **A Makefile build and a release build print different versions** `(low)` | `make build` stamps `git describe --tags --always --dirty` (for example `v0.3.0-5-g81451b7-dirty`), while GoReleaser stamps the tag without its leading `v`. | `Makefile:2-4`, `Dockerfile:13`, `.goreleaser.yaml:23` | Compare `amnezigo version` output only between binaries built the same way. |
| **`awg show dump` field positions are a contract** `(low)` | The 3.x data lands at 1-based fields 20-28 of the interface record (20 header-protection key, 21 content padding addition, 22-26 the five timers, 27 random trailers, 28 disable cookies; the interface fwmark follows at 29); `awg show all dump` additionally prefixes the interface name. | `e2e/harness_test.go:34-64`, `e2e/harness_test.go:348-365` | Parse by position only with the matching engine version; a 2.0 config on a 3.1 engine reports `(none)` and `off`. |
| **Tests use stdlib `testing` only** `(info)` | Assertions are manual `if got != want { t.Errorf(...) }`; no `testify` import exists. | all `*_test.go` | Follow the manual-assertion style when contributing. |
| **Tests are path-relative — run `go test ./...` from the repository root** `(medium)` | Tests reference fixtures via `filepath.Join("testdata", ...)`, which only resolves from the module root; running from a subdirectory fails with missing-testdata errors. | `loader_test.go` and other `*_test.go` | Run `go test ./...` from the repository root. |
| **Error substrings are a public contract** `(medium)` | Tests assert two-step: `err != nil`, then `strings.Contains(err.Error(), expectedSubstring)`. Changing a message breaks tests and any tooling that matches on it. | `AGENTS.md`, `*_test.go` | Treat error text as stable; update tests and callers together. |
