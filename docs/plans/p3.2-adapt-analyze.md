## 1. Context

`amnezigo analyze` (shipped in P1.4) reports the on-the-wire profile of a server config: padded handshake sizes, junk range, header ranges, per-peer I-packet sizes, packet ordering, and fingerprint risk heuristics. Today it only accepts INI server configs (`awg0.conf`) loaded via `Manager.Load()`.

The P2 declarative pivot introduces a new input format: JSON/Jsonnet manifests (`amnezigo.json` / `amnezigo.jsonnet`) that declare the full network topology. Users will want to run `amnezigo analyze` on their manifest to preview what the obfuscation profile looks like *before* running `generate`. This is especially useful for preset evaluation: "what does `home-balanced` look like on the wire?"

**Key insight**: `analyze` does not need generated output. It computes the profile entirely from obfuscation parameters (S1-S4, Jc/Jmin/Jmax, H1-H4) plus protocol templates for I-packet derivation. These parameters are fully determined by the manifest's `obfuscation` block (which is either a preset name or explicit values). Therefore, `analyze` can work directly on the manifest without running `generate` first.

The current flow is:

```text
awg0.conf → Manager.Load() → ServerConfig → Analyze() → AnalysisReport
```

The new flow adds a parallel path:

```text
amnezigo.json → LoadManifest() → Manifest → ManifestToAnalysisInput() → ServerConfig → Analyze() → AnalysisReport
```

The `Analyze()` function, `AnalysisReport` struct, formatters, and heuristics are completely unchanged. The only new code is:

1. A converter from `Manifest` to `ServerConfig` (resolving presets along the way).
2. CLI format detection logic to choose between INI and manifest loading.
3. Multi-peer support using manifest peer names.

## 2. Goal

Extend `amnezigo analyze` to accept manifest files alongside INI configs. Concrete deliverables:

- `amnezigo analyze --manifest amnezigo.json` analyzes the manifest's obfuscation profile.
- `amnezigo analyze --config awg0.conf` continues to work exactly as before (zero behavioral change for existing users).
- Format auto-detection based on file extension when only `--manifest` or `--config` is provided.
- `--peer NAME` works with manifest peer names.
- Preset resolution: if the manifest specifies `obfuscation.preset = "home-balanced"`, the analyzer resolves it to concrete parameters via `GetPreset()` before calling `Analyze()`.
- Per-peer protocol override: if a manifest peer specifies a per-peer `protocol` field, the analyzer uses it; otherwise falls back to the manifest-global `obfuscation.protocol` or the CLI `--protocol` flag.
- Output format and content are identical whether analyzing a manifest or its generated output (given the same obfuscation parameters and protocol).

Out of scope for **this PR** (deferred or excluded):

- `amnezigo analyze --preset home-balanced` shorthand (analyzing a preset directly without a manifest file). Useful but separate; can be added as a small follow-up.
- Running `generate` in dry-run mode during analysis to catch generation-time errors.
- Validating the manifest schema (that is P3.1's responsibility; analyze assumes a structurally valid manifest).
- Changes to `Analyze()`, `AnalysisReport`, formatters, or heuristics. None needed.
- Server-vs-client peer distinction in the manifest. Analysis treats all peers the same (each gets I-packets generated). This is correct: server peers in a star topology receive I-packets from their clients, but the analysis shows what the I-packets *look like*, which is symmetric.

## 3. Goal — Explicit Scope Boundary

This extension MUST NOT:

- Break existing `--config awg0.conf` behavior. Zero regression.
- Modify the `Analyze()` function signature or `AnalysisReport` struct. The converter produces a `ServerConfig` that feeds into the existing function.
- Introduce new dependencies (the manifest types, loader, and preset system are all from P2.1, P2.2, and P1.5 respectively).
- Add new heuristic codes. The existing RISK001-RISK009 work identically on manifest-derived configs.
- Prompt the user for input, mutate files, or exit non-zero on findings.

## 5. Architecture Decisions

### 5.1 Converter placement — `manifest_analysis.go` at the package root

**Decision**: new file `manifest_analysis.go` in the package root (alongside `analysis.go`, `manifest.go`).

**Alternatives considered**:

- Inside `analysis.go` — would grow the file past 700 LOC, mixing manifest-specific logic with format-agnostic analysis.
- Inside `manifest.go` — couples the manifest type definitions to the analysis system.
- As a method on `Manifest` — requires `Manifest` to know about `ServerConfig`, which is a valid coupling but better expressed as a standalone function for testability.

**Rationale**: the converter is one function (~80 LOC) with a clear responsibility: "transform manifest data into the shape `Analyze()` expects". It depends on both `Manifest` (from P2.1) and `ServerConfig` + `Preset` (existing types). A standalone file keeps this bridge explicit.

### 5.2 Converter signature — function, not method

**Decision**: `ManifestToAnalysisInput(m Manifest) (ServerConfig, error)` as a package-level function.

**Rationale**:

- Testable independently of the manifest loader.
- No state; pure transformation.
- Error returns cover: unknown preset name, malformed H-range strings, missing required fields.
- Returns `ServerConfig` because `Analyze()` already accepts `ServerConfig`. No new type needed.

### 5.3 Flag design — `--manifest PATH` alongside existing `--config PATH`

**Decision**: add `--manifest PATH` flag to the analyze command. Mutually exclusive with `--config`. When neither is provided, default behavior (load `awg0.conf`) is unchanged.

**Alternatives considered**:

- Auto-detection on `--config` by extension (`.json`/`.jsonnet` = manifest, `.conf` = INI). Appealing but breaks the explicit contract: `--config` historically means "INI server config". Overloading it silently is surprising.
- Single `--input` flag replacing both. Would break backward compatibility.

**Rationale**: explicit flags make the input type unambiguous. The CLI validates that at most one of `--manifest` and `--config` is provided.

**Auto-detection within `--manifest`**: when the `--manifest` path ends with `.json` or `.jsonnet`, the loader (P2.2) handles the distinction internally. The CLI does not need to distinguish.

### 5.4 Per-peer protocol resolution — cascade: CLI flag > peer manifest > global manifest > "random"

**Decision**: protocol for I-packet generation follows a four-level cascade:

1. CLI `--protocol` flag (explicit user override, highest priority).
2. Per-peer `protocol` field in the manifest (`peers.phone.protocol = "sip"`).
3. Global `obfuscation.protocol` in the manifest (`obfuscation.protocol = "quic"`).
4. Default `"random"` (existing behavior).

**Rationale**: matches the manifest's design intent (per-peer overrides) while preserving CLI ergonomics. The CLI flag is a session-level override for quick experimentation ("what would all peers look like with DTLS?") without editing the manifest.

**Implementation**: the converter populates a per-peer protocol field. The CLI constructs one `AnalyzeOptions` per peer when protocols differ. When all peers share the same protocol (common case), a single `Analyze()` call suffices.

**Simplification decision**: in the MVP, the CLI `--protocol` flag overrides ALL peers uniformly. Per-peer protocol differentiation from the manifest is honored only when `--protocol` is not explicitly set. This keeps the implementation simple (one `Analyze()` call) and matches the current behavior where `--protocol` is a global override.

### 5.5 Peer construction — manifest peers become `PeerConfig` stubs

**Decision**: the converter creates `PeerConfig` entries from the manifest's peer map. Only `Name` and `AllowedIPs` (from the peer's `address` field) are populated. Private keys, public keys, and PSKs are NOT populated (they are irrelevant to analysis).

**Rationale**: `Analyze()` uses `PeerConfig.Name` for report labeling and iterates over peers for I-packet generation. It does not access cryptographic fields. Leaving them empty is correct.

### 5.6 Server peer identification — include or exclude from analysis?

**Decision**: include ALL peers, including the server peer. Do not filter by role.

**Rationale**: in AWG, I-packets are sent from client to server during the handshake. The server peer itself does not send I-packets. However, the analysis shows "what I-packets would be generated for a peer with these obfuscation parameters" — which is meaningful for ALL peers. Excluding the server peer would be confusing ("why is my server not in the analysis?"). Users can filter with `--peer NAME` if they want to focus on a specific peer.

### 5.7 ListenPort — use server peer's listen_port or 0

**Decision**: when analyzing a manifest, `ConfigInfo.ListenPort` is populated from the server peer's `listen_port` field. If no server peer exists or `listen_port` is 0, the report shows 0.

**Rationale**: `ListenPort` is informational in the analysis (it appears in the report header). It does not affect any calculation. Showing the manifest's value is correct.

### Step B — Implement converter (Green)

Fill in `ManifestToAnalysisInput` and `resolveObfuscation`:

```go
func ManifestToAnalysisInput(m Manifest) (ServerConfig, error) {
    obf, err := resolveObfuscation(m.Obfuscation)
    if err != nil {
        return ServerConfig{}, fmt.Errorf("resolving obfuscation: %w", err)
    }

    cfg := ServerConfig{
        Interface: InterfaceConfig{
            MTU: m.Network.MTU,
        },
        Obfuscation: obf,
    }

    // Find server peer for ListenPort.
    for _, peer := range m.Peers {
        if peer.ListenPort > 0 {
            cfg.Interface.ListenPort = peer.ListenPort
            break
        }
    }

    // Build peer stubs in deterministic order.
    // Manifest peer map iteration order is non-deterministic; sort by name.
    names := sortedPeerNames(m.Peers)
    for _, name := range names {
        peer := m.Peers[name]
        cfg.Peers = append(cfg.Peers, PeerConfig{
            Name:       name,
            AllowedIPs: peer.Address,
        })
    }

    return cfg, nil
}

func resolveObfuscation(obf ObfuscationManifest) (ServerObfuscationConfig, error) {
    var base ServerObfuscationConfig

    if obf.Preset != "" {
        preset, err := GetPreset(obf.Preset)
        if err != nil {
            return ServerObfuscationConfig{}, err
        }
        base = preset.ToServerObfuscation()
    }

    // Overlay explicit params (non-zero values override preset).
    if obf.S1 != 0 { base.S1 = obf.S1 }
    if obf.S2 != 0 { base.S2 = obf.S2 }
    if obf.S3 != 0 { base.S3 = obf.S3 }
    if obf.S4 != 0 { base.S4 = obf.S4 }
    if obf.Jc != 0 { base.Jc = obf.Jc }
    if obf.Jmin != 0 { base.Jmin = obf.Jmin }
    if obf.Jmax != 0 { base.Jmax = obf.Jmax }
    // H-range overlay: parse "min-max" strings if present.
    // (Exact parsing depends on P2.1 schema; adapt when types are final.)

    return base, nil
}
```

**Helper** `sortedPeerNames` returns the peer map keys in alphabetical order for deterministic output:

```go
func sortedPeerNames(peers map[string]PeerManifest) []string {
    names := make([]string, 0, len(peers))
    for name := range peers {
        names = append(names, name)
    }
    sort.Strings(names)
    return names
}
```

```go
func TestAnalyze_ManifestEquivalence(t *testing.T) {
    // Build a ServerConfig by hand with home-balanced preset values.
    preset, _ := amnezigo.GetPreset("home-balanced")
    iniCfg := amnezigo.ServerConfig{
        Interface: amnezigo.InterfaceConfig{
            MTU:        1280,
            ListenPort: 51820,
        },
        Obfuscation: preset.ToServerObfuscation(),
        Peers: []amnezigo.PeerConfig{
            {Name: "phone", AllowedIPs: "10.0.0.2/32"},
        },
    }

    // Build the same config from a manifest.
    manifest := amnezigo.Manifest{
        Version:     1,
        Network:     amnezigo.NetworkManifest{MTU: 1280},
        Obfuscation: amnezigo.ObfuscationManifest{Preset: "home-balanced"},
        Peers: map[string]amnezigo.PeerManifest{
            "server": {Address: "10.0.0.1/24", ListenPort: 51820},
            "phone":  {Address: "10.0.0.2/32"},
        },
    }
    manifestCfg, err := amnezigo.ManifestToAnalysisInput(manifest)
    if err != nil { t.Fatal(err) }

    // Analyze both with the same seed for reproducibility.
    seed := newSeededReader(42)
    opts := amnezigo.AnalyzeOptions{Protocol: "quic", Rand: seed, PeerName: "phone"}

    iniReport := amnezigo.Analyze(iniCfg, opts)

    seed2 := newSeededReader(42) // reset seed
    opts2 := amnezigo.AnalyzeOptions{Protocol: "quic", Rand: seed2, PeerName: "phone"}
    manifestReport := amnezigo.Analyze(manifestCfg, opts2)

    // Compare non-random fields.
    if iniReport.Config.MTU != manifestReport.Config.MTU {
        t.Errorf("MTU mismatch: %d vs %d", iniReport.Config.MTU, manifestReport.Config.MTU)
    }
    if iniReport.Handshake != manifestReport.Handshake {
        t.Errorf("Handshake mismatch")
    }
    if iniReport.Junk != manifestReport.Junk {
        t.Errorf("Junk mismatch")
    }
    if iniReport.Headers != manifestReport.Headers {
        t.Errorf("Headers mismatch")
    }
}
```

## 9. Risks and Edge Cases

| Risk | Assessment / Mitigation |
| --- | --- |
| P2.1 manifest schema changes after this plan is written | The converter is a single function. Schema changes affect only `ManifestToAnalysisInput` and its tests — localized impact. The plan specifies the expected schema based on the roadmap draft and documents the assumption explicitly. |
| P2.2 `LoadManifest` signature changes | Only one call site in `runAnalyze`. Adapt the arguments. |
| Manifest with zero peers | Same behavior as INI config with zero peers: report omits the per-peer section, emits RISK008 finding. No special handling needed. |
| Manifest with only a server peer (no clients) | Server peer is included in analysis (§ 5.6). The report shows one peer. I-packets are generated normally. |
| Manifest peer map ordering is non-deterministic | `sortedPeerNames` sorts alphabetically. Output is deterministic across runs. |
| Preset resolution failure (unknown preset name) | `GetPreset` returns a descriptive error listing available presets. `ManifestToAnalysisInput` wraps and returns it. CLI exits non-zero with the error message. |
| Explicit params with value 0 (intentionally zero S1, for example) | The overlay logic uses `!= 0` to detect overrides. This means `s1: 0` in a manifest with a preset will NOT override the preset's S1 to 0. This is a known limitation. Mitigation: document it. Users who genuinely want S1=0 should not use a preset. Alternative: use a pointer-based optional type (`*int`) in the manifest schema (P2.1 decision, not this plan's). |
| `--manifest` and `--config` both provided | Detected by mutual exclusion check in `runAnalyze`. Returns clear error. |
| Both flags absent (default behavior) | Falls through to existing `--config awg0.conf` default. Zero regression. |
| Jsonnet evaluation failure | Handled by `LoadManifest` (P2.2). Error propagates through `runAnalyze`. |
| Per-peer protocol override from manifest | Honored only when CLI `--protocol` is not explicitly set. When CLI override is active, all peers use the CLI-specified protocol. This is a deliberate simplification (§ 5.4). |
| Large manifest (100+ peers) | Same as INI config with 100+ peers: output is long, use `--peer NAME` to narrow. No performance concern — analysis is arithmetic, not I/O. |
| `go vet` / `golangci-lint` regressions | Run before commit. The new code follows existing patterns (no new linter rules needed). |

## 11. Out of Scope (Explicit)

The following are **deliberately excluded** from this PR. If any come up during implementation, do not include them; note them for follow-up.

- **`amnezigo analyze --preset home-balanced`** — analyzing a preset directly without a manifest file. Useful shorthand but separate from manifest support. Can be added as a small follow-up PR (~30 LOC: construct a synthetic `Manifest` from the preset, call `ManifestToAnalysisInput`, done).
- **Manifest validation during analysis** — running `ValidateManifest()` (P3.1) during manifest loading to surface validation errors as findings. Analysis assumes a structurally valid manifest. Users should run `amnezigo validate` separately.
- **Changes to `Analyze()`, `AnalysisReport`, formatters, or heuristics** — none needed. The entire adaptation is pre-processing (converter + CLI wiring).
- **Per-peer protocol differentiation in multi-peer analysis** — when `--protocol` is not set and peers have different per-peer protocols, the MVP uses the manifest's global protocol for all peers. Full per-peer protocol support (running `Analyze()` once per protocol group) is a follow-up.
- **Server-vs-client peer role awareness** — the analysis does not distinguish server and client peers. All peers get I-packets generated. This is correct for the "what does the profile look like" use case.
- **Credential fields in `ServerConfig`** — `PrivateKey`, `PublicKey`, `PresharedKey` are not populated by the converter. They are irrelevant to analysis.
- **`--jpath` flag for jsonnet imports** — deferred to the `generate` command (P2.4). If needed for analyze, thread through `LoadManifest`'s second argument.
- **YAML manifest support** — only JSON and Jsonnet per P2.1/P2.2.
- **Modifications to `presets.go`** — the existing `GetPreset` and `ToServerObfuscation` are sufficient.
