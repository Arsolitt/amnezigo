# P2.5 — Remove Legacy Imperative CLI

> Atomic execution plan for roadmap item **P2.5** (see `docs/roadmap.md` lines 589-634).
>
> **Status**: Ready for implementation (after P2.4 merges)
> **Estimated diff**: ~-3200 LOC deleted, ~+80 LOC modified across 2 modified files + 1 new test file + 2 doc updates. Net negative — this is a cleanup PR.
> **Depends on**: **P2.4** (delivers `generate` command and full declarative pipeline). All prior P2 items (P2.1 schema, P2.2 loader, P2.3 credentials) are transitive dependencies via P2.4.
> **Blocks**: **P3.1** (adapt `validate` for manifests), **P3.2** (adapt `analyze` for manifests) — those commands assume the imperative CLI is already gone and `manager.go` is deleted.
> **Independent of**: P3.3 (preset integration with manifests), deferred backlog items.

---

## 1. Context

`amnezigo` is transitioning from an imperative CLI workflow (`init → add → edit → remove → export → list`) to a declarative config-driven architecture centered on a single `generate` command (P2.4). Decision 10 in the roadmap (`docs/roadmap.md` line 25) is explicit: "No backward compatibility shims." The old commands and their backing `Manager` struct must be deleted, not deprecated.

The imperative CLI currently comprises six commands (`init`, `add`, `edit`, `remove`, `export`, `list`), each backed by `Manager` methods in `manager.go`. After P2.4 lands, these commands are redundant — `generate` replaces the entire workflow. Maintaining both paths doubles the bug surface, confuses users, and blocks P3 work that assumes the new architecture.

**Why this must be a single PR, not split**: The old commands depend on `Manager`, and `Manager` depends on functions (`LoadServerConfig`, `SaveServerConfig`) that are also used by other code. Splitting "delete commands" from "delete Manager" would leave dead code in between. One atomic PR that removes all legacy paths and cleans up the dependency graph is the correct approach.

## 2. Goal

Delete all imperative CLI commands and their backing code. After this PR:

- `amnezigo --help` shows only: `generate`, `validate`, `analyze`
- `amnezigo init` / `add` / `edit` / `remove` / `export` / `list` produce "unknown command" errors
- `manager.go` and `manager_test.go` are deleted
- All six CLI files and their test files are deleted
- `go vet ./...` and `golangci-lint run` pass with zero issues (no dead code)
- Documentation reflects the new command set

**In scope (this PR):**

- Delete imperative CLI files and their tests
- Delete `manager.go` and `manager_test.go`
- Update `cli.go` command registration
- Migrate `LoadServerConfig` and `SaveServerConfig` to survive (used by other code)
- Update `analyze.go` to use `LoadServerConfig` directly instead of `Manager`
- Update documentation (`docs/cli-reference.md`, `README.md`)

**Explicit out-of-scope:**

- Refactoring `validate` or `analyze` to accept manifests — that is P3.1 and P3.2
- Adding the `generate` command — that is P2.4 (must already be merged)
- Any new features or behavior changes to the surviving commands

**Relocation decision for `LoadServerConfig` / `SaveServerConfig`**: These are standalone functions that do not depend on the `Manager` struct. They belong in `parser.go` (which already has `ParseServerConfig`) or in a new `config_io.go`. Since `LoadServerConfig` wraps `ParseServerConfig` (parser.go) and `SaveServerConfig` wraps `WriteServerConfig` (writer.go), placing them adjacent to the functions they wrap is logical. Move `LoadServerConfig` to `parser.go` (it wraps parse) and `SaveServerConfig` to `writer.go` (it wraps write). This avoids creating a new file and keeps related code together.

## 4. Architecture Decisions

### 4.1 One PR, not two

**Decision**: Ship P2.5 as a single PR deleting all legacy code at once.

**Rationale**: Splitting into "delete CLI files" then "delete Manager" creates a commit where CLI files are gone but Manager has no callers other than analyze — `golangci-lint` would flag unused exports. A single PR is atomically correct: every deleted symbol has its callers deleted in the same diff.

### 4.2 Relocate `LoadServerConfig` and `SaveServerConfig`

**Decision**: Move `LoadServerConfig` to `parser.go` and `SaveServerConfig` to `writer.go`.

**Rationale**:

- `LoadServerConfig` is `Open + ParseServerConfig` — it belongs next to the parser.
- `SaveServerConfig` is `Create + WriteServerConfig + Rename` — it belongs next to the writer.
- No new files needed. No import changes (both functions stay in package `amnezigo`).
- Tests for these functions move to `parser_test.go` and `writer_test.go` respectively.

### 4.3 Migrate `analyze` from Manager to direct call

**Decision**: Replace `mgr := amnezigo.NewManager(cfgFile)` + `mgr.Load()` with `amnezigo.LoadServerConfig(cfgFile)` in `analyze.go`.

**Rationale**: `Manager.Load()` is literally `return LoadServerConfig(m.ConfigPath)`. The abstraction adds nothing. Direct call is clearer and removes the Manager dependency.

### 4.4 Remove `cfgFile` shared variable — scope and cleanup

**Decision**: Keep `cfgFile` in `cli.go` for now. After this PR, only `analyze.go` uses it (and the future `generate.go` from P2.4). The variable is harmless; cleaning it up is a refactor for another day.

**Rationale**: The `cfgFile` var in `cli.go:22` is a package-global used by multiple commands. After deletion, only `analyze.go` still references it. Removing it now would require converting analyze to use command-local flag vars — a refactor that muddies the deletion-focused PR. Leave it; P3.2 (adapt analyze for manifests) will likely rewrite the entire flag structure anyway.

### 4.5 Constants cleanup in `cli.go`

**Decision**: Remove `tabPadding` and `separatorWidth` constants from `cli.go`. Keep `outputFormatText` and `outputFormatJSON`.

**Rationale**: `tabPadding` (line 11) and `separatorWidth` (line 12) are used only by `list.go:39,41`. Once `list.go` is deleted, they become dead code. `outputFormatText` and `outputFormatJSON` are used by `validate.go` and `analyze.go` — they survive.

### 4.6 Documentation strategy

**Decision**: Rewrite `docs/cli-reference.md` to cover only the three surviving commands (`generate`, `validate`, `analyze`). Remove sections for deleted commands. Update the overview text and table of contents.

**Rationale**: Keeping deleted command docs confuses users. The roadmap decision is "no backward compatibility shims" — docs should match.
