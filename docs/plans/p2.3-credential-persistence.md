## 1. Context

`amnezigo` generates AmneziaWG configuration files. Each peer in a WireGuard/AmneziaWG network has:

- A **keypair** (PrivateKey + PublicKey) — identifies the peer cryptographically.
- A **preshared key** (PSK) — shared between each peer-to-peer connection for post-quantum resistance.

In the current imperative workflow (`init` → `add` → `export`), keys are generated once during `AddPeer` (`manager.go:126-127`) and stored inside the server config's `[Peer]` section (`writer.go:69-86`). The config file itself is the sole persistence layer.

The new declarative architecture (P2.1-P2.5) replaces this with `amnezigo generate`, which reads a manifest and produces per-peer output directories. Without credential persistence, every `generate` run would call `GenerateKeyPair()` and `GeneratePSK()` fresh — producing entirely new keys, breaking all existing peer connections, and requiring simultaneous redeployment of every config.

**Why credentials live in the output configs, not a separate state file:**

The cheburbox project (`/home/arsolitt/projects/cheburbox/config/persistence.go`) established the pattern: credentials are extracted from the previously generated output (`config.json`), not from a separate `.credentials.json` or `.state` file. Benefits:

1. **No extra file to manage** — output configs are already versioned, backed up, deployed. A separate state file doubles the drift surface.
2. **Single source of truth** — the config on disk IS the state. No reconciliation needed between state file and actual output.
3. **Inspection** — users can `cat server/awg0.conf` and see the PrivateKey. No tooling needed to inspect state.
4. **Atomicity** — if generation fails mid-way, old configs (with old keys) remain untouched. No partial state file corruption.

The amnezigo implementation adapts this pattern: read existing `awg0.conf` files from per-peer output directories, extract PrivateKey/PublicKey/PresharedKey, and reuse them when the peer still exists in the manifest.

**Credential topology in WireGuard/AmneziaWG:**

```text
Server (server peer)
├── PrivateKey: server_priv     ← persisted in server/awg0.conf [Interface]
├── PublicKey:  server_pub      ← derived from server_priv, appears in client configs
│
├── Peer: phone
│   ├── PrivateKey: phone_priv  ← persisted in phone/awg0.conf [Interface]
│   ├── PublicKey:  phone_pub   ← derived from phone_priv, appears in server/awg0.conf [Peer]
│   └── PresharedKey: psk_phone ← shared, appears in BOTH server/awg0.conf [Peer] and phone/awg0.conf [Peer]
│
└── Peer: laptop
    ├── PrivateKey: laptop_priv
    ├── PublicKey:  laptop_pub
    └── PresharedKey: psk_laptop
```

Key relationships:

- Each peer has exactly one keypair (PrivateKey → PublicKey via X25519 scalar mult).
- Each peer-to-server connection has exactly one PSK.
- The server's PublicKey appears in every client config's `[Peer].PublicKey`.
- Each client's PublicKey appears in the server config's corresponding `[Peer].PublicKey`.
- PSKs are symmetric — the same value appears on both sides of the connection.

## 2. Goal

Implement `LoadCredentials(outputDir string) (*PersistedCredentials, error)` that scans existing output directories, reads `awg0.conf` files, and extracts all keypairs and PSKs. The returned struct is consumed by P2.4's `Generate` pipeline to decide: reuse existing keys for known peers, generate fresh keys for new peers only.

**In scope (this PR):**

- New type `PersistedCredentials` holding server credentials + per-peer credentials map.
- New type `PeerCredentials` holding a single peer's PrivateKey, PublicKey, PresharedKey.
- `LoadCredentials(outputDir string) (*PersistedCredentials, error)` — walks output subdirectories, parses `awg0.conf` files, extracts credentials.
- Server credential extraction from `output/server/awg0.conf` `[Interface]` section (PrivateKey, PublicKey).
- Client credential extraction from `output/<peer>/awg0.conf` `[Interface]` section (PrivateKey) and `[Peer]` section (PresharedKey).
- Graceful handling of missing output directory (first run — return empty credentials, not error).
- Graceful handling of missing individual peer directories (new peer — no credentials for that peer).
- `EmptyCredentials()` constructor for first-run / `--full-reset` scenarios.
- Full test suite: persist → reload → verify same keys, empty dir, partial dir, malformed config.

**Explicit out-of-scope (deferred to P2.4):**

- The `--full-reset` CLI flag. This PR provides `EmptyCredentials()` as the mechanism; P2.4 wires it to the flag.
- The `Generate` pipeline that consumes `PersistedCredentials` to decide new-vs-reuse.
- Orphan detection (peer directory exists but peer not in manifest). P2.4 may warn; this PR does not.
- Client config parsing (`ParseClientConfig` does not exist — see `parser.go:213`). We parse client configs using a new lightweight extractor, not a full parser.
- I-packet (I1-I5) persistence. I-packets are intentionally regenerated on every run for fingerprint resistance (roadmap decision in P2.4 brainstorm). Only keypairs and PSKs are persisted.

**Key insight from the current codebase:**

The server config file (`awg0.conf`) already stores everything we need for credential persistence:

- `[Interface].PrivateKey` — server private key
- `[Interface].PublicKey` — server public key (optional; can be derived)
- `[Peer].PublicKey` — each peer's public key
- `[Peer].PresharedKey` — each peer's PSK
- `[Peer].#_PrivateKey` — each peer's private key (metadata comment)
- `[Peer].#_Name` — each peer's name (metadata comment for lookup)

In the new architecture with per-peer output directories, the server config has this information for all peers, AND each client config has the individual peer's credentials. We can extract from either source, but the server config is the single richest source — it has all peers in one file.

However, in the new declarative architecture, the output structure changes:

```text
output/
  server/awg0.conf    — server config (has all peer pubkeys + PSKs + private keys as comments)
  phone/awg0.conf     — client config (has phone's privkey + server's pubkey + PSK)
  laptop/awg0.conf    — client config (has laptop's privkey + server's pubkey + PSK)
```

**Extraction strategy**: Read the server output config as the primary source. It contains the server keypair in `[Interface]` and all peer credentials in `[Peer]` sections (including private keys as `#_PrivateKey` metadata comments). Fall back to reading individual client configs only if the server config is missing or incomplete.

## 4. Architecture Decisions

### 4.1 Server config as primary credential source

**Decision**: `LoadCredentials` reads `<outputDir>/<serverPeerName>/awg0.conf` using the existing `ParseServerConfig` parser. The server config's `[Interface]` section provides server credentials; its `[Peer]` sections provide all peer credentials (including private keys via `#_PrivateKey` metadata comments and names via `#_Name`).

**Rationale**:

- The server config is the single file that contains ALL credentials — server keypair, all peer public keys, all PSKs, and all peer private keys (as metadata comments).
- `ParseServerConfig` (`parser.go:38-41`) already parses all these fields: `InterfaceConfig.PrivateKey`, `InterfaceConfig.PublicKey`, `PeerConfig.PublicKey`, `PeerConfig.PresharedKey`, `PeerConfig.PrivateKey` (from `#_PrivateKey`), `PeerConfig.Name` (from `#_Name`).
- No new parser needed — full reuse of existing infrastructure.
- Avoids the complexity of reading N client configs when one file suffices.

**Consequence**: If someone manually deletes the server output config but keeps client configs, credentials are lost. This is acceptable — the server config is the canonical output, and losing it means the server can't operate anyway. Document this in the plan.

### 4.2 Client config fallback for peer credentials

**Decision**: If the server config is missing (first run for a server but client dirs exist from migration), attempt to read individual client configs from `<outputDir>/<peerName>/awg0.conf`. Extract `[Interface].PrivateKey` and `[Peer].PresharedKey` using a lightweight INI scanner (not a full parser).

**Rationale**:

- Covers the migration scenario: user has client configs from the old imperative CLI but regenerated the server.
- A lightweight scanner avoids depending on a `ParseClientConfig` function that does not exist.
- The scanner needs only two fields: `PrivateKey` from `[Interface]` and `PresharedKey` from `[Peer]`. No obfuscation params, no I1-I5, no endpoint.

**Consequence**: The fallback is best-effort. If client configs are also missing, fresh keys are generated (clean first-run behavior).

### 4.3 Credential types — `PersistedCredentials` and `PeerCredentials`

**Decision**: Define two types in `credentials.go`:

```go
// PeerCredentials holds the cryptographic material for a single peer.
type PeerCredentials struct {
    PrivateKey   string // base64-encoded X25519 private key
    PublicKey    string // base64-encoded X25519 public key (derived from PrivateKey)
    PresharedKey string // base64-encoded 32-byte PSK (per peer-to-server connection)
}

// PersistedCredentials holds all credentials extracted from existing output configs.
type PersistedCredentials struct {
    // Server holds the server peer's keypair. Empty on first run.
    Server PeerCredentials
    // Peers maps peer name → credentials. Only peers found in output are present.
    Peers map[string]PeerCredentials
}
```

**Rationale**:

- Mirrors the cheburbox pattern (`PersistedCredentials` with inner maps keyed by identifier) but simplified — WireGuard has only keypairs and PSKs, not UUIDs/passwords/Reality keys.
- `PeerCredentials` groups PrivateKey + PublicKey + PresharedKey as a unit. Server credentials use the same type but with PresharedKey empty (servers don't have PSKs to themselves).
- Map keyed by peer name (from `#_Name` metadata comment) allows O(1) lookup when the pipeline checks "does this manifest peer have existing credentials?"
- No `CreatedAt` in credentials — timestamp is metadata, not a credential. If needed later, it can be added without breaking the struct.

**Alternative rejected**: Storing credentials as a flat `map[string]PeerCredentials` without a separate `Server` field. Rejected because the server keypair has different semantics (no PSK, no "name" in the manifest sense) and conflating it with peer entries would require a sentinel key (e.g. `"__server__"`) — ugly.

### 4.4 Empty credentials on missing output — not an error

**Decision**: `LoadCredentials` returns `EmptyCredentials()` (zero-value with initialized map) when the output directory does not exist. This is the expected first-run path.

**Rationale**:

- Follows the cheburbox pattern exactly: `LoadPersistedCredentials` returns `EmptyPersistedCredentials()` when the config file does not exist (`persistence.go:48-50`).
- First run: no output directory exists → empty credentials → all keys generated fresh. Natural flow.
- Avoids forcing callers to check for a sentinel error and branch. The pipeline logic is uniform: "for each peer, if credentials exist, reuse; else generate."

### 4.5 No separate state file

**Decision**: Credentials are persisted exclusively in the generated output configs. No `.amnezigo-state.json`, no `.credentials.json`, no SQLite.

**Rationale**:

- Same rationale as cheburbox: the output IS the state. Adding a separate file doubles the drift surface without adding capability.
- If the user deletes output and re-runs, they get fresh keys. This is correct behavior — if the output is gone, the old deployment is gone too.
- Version control: output configs can be committed (if desired) or `.gitignore`d. No extra file to manage.
- Rollback: `git checkout output/` restores old keys. No state-file version migration needed.

### 4.6 Server peer name discovery

**Decision**: `LoadCredentials` accepts an explicit `serverPeerName string` parameter identifying which subdirectory of `outputDir` contains the server config. The manifest (P2.1) determines this — the peer with `endpoint` + `listen_port` is the server peer.

**Rationale**:

- The output directory structure uses peer names as subdirectory names: `output/server/awg0.conf`, `output/phone/awg0.conf`. The server peer's name in the manifest determines which directory to read for server credentials.
- Hardcoding `"server"` would be incorrect — the manifest allows any name for the server peer.
- Passing the name explicitly from the pipeline (which already resolved the server peer from the manifest) avoids duplicating manifest-resolution logic in the credential loader.

### 4.7 Lightweight client config credential extraction

**Decision**: Implement `extractClientCredentials(configPath string) (PeerCredentials, error)` as a focused INI scanner that reads only `[Interface].PrivateKey` and `[Peer].PresharedKey` from a client config file. Not a full `ParseClientConfig`.

**Rationale**:

- `ParseClientConfig` does not exist and writing a full client parser is P1.3-followup scope (per `parser.go:213` comment). This PR should not take on that debt.
- A credential extractor needs exactly two fields from a client config. A 30-line scanner is proportionate; a full parser is not.
- The scanner reuses `bufio.Scanner` + `strings.SplitN` — the same idiom as `ParseServerConfigWithOptions` — but without the 250-line switch statement for all obfuscation parameters.
- PublicKey can be derived from PrivateKey via `DerivePublicKey()` (`keys.go:34-54`), so we only need to read PrivateKey.

### 4.8 Config file name convention

**Decision**: The expected file name inside each output subdirectory is `awg0.conf`. This matches the current generator's output and the `awg-quick` convention.

**Rationale**:

- Current `WriteServerConfig` and `WriteClientConfig` produce `awg0.conf` (wired through the CLI's `--config` flag defaulting to `awg0.conf` — see `internal/cli/export.go:40`).
- P2.4 will also use `awg0.conf` as the output file name in each peer directory.
- A constant `const outputConfigName = "awg0.conf"` makes this a single edit point if it ever changes.

```go
const outputConfigName = "awg0.conf"

// LoadCredentials reads existing output configs from outputDir and extracts
// all persisted credentials. Returns empty credentials (not error) if the
// output directory or server config does not exist (first-run path).
//
// The serverPeerName identifies which subdirectory contains the server config.
// Peer credentials are extracted from the server config's [Peer] sections
// (which include #_Name and #_PrivateKey metadata comments).
func LoadCredentials(outputDir, serverPeerName string) (*PersistedCredentials, error) {
    serverConfigPath := filepath.Join(outputDir, serverPeerName, outputConfigName)

    serverCfg, err := LoadServerConfig(serverConfigPath)
    if os.IsNotExist(err) {
        return EmptyCredentials(), nil
    }
    if err != nil {
        return nil, fmt.Errorf("load server config for credentials: %w", err)
    }

    creds := EmptyCredentials()

    // Extract server keypair from [Interface].
    creds.Server = PeerCredentials{
        PrivateKey: serverCfg.Interface.PrivateKey,
        PublicKey:  serverCfg.Interface.PublicKey,
    }

    // Extract peer credentials from [Peer] sections.
    for _, peer := range serverCfg.Peers {
        if peer.Name == "" {
            continue // unnamed peers cannot be matched to manifest entries
        }
        creds.Peers[peer.Name] = PeerCredentials{
            PrivateKey:   peer.PrivateKey,
            PublicKey:    peer.PublicKey,
            PresharedKey: peer.PresharedKey,
        }
    }

    return creds, nil
}
```

Note: `LoadServerConfig` (`manager.go:316-324`) already handles `os.Open` and delegates to `ParseServerConfig`. The `os.IsNotExist` check catches the first-run case.

```go
// extractClientCredentials reads a client config file and extracts
// PrivateKey from [Interface] and PresharedKey from [Peer]. Lightweight
// scanner — not a full ParseClientConfig.
func extractClientCredentials(configPath string) (PeerCredentials, error) {
    f, err := os.Open(configPath)
    if err != nil {
        return PeerCredentials{}, err
    }
    defer f.Close()

    var creds PeerCredentials
    var currentSection string
    scanner := bufio.NewScanner(f)
    for scanner.Scan() {
        line := strings.TrimSpace(scanner.Text())
        if line == "" || (strings.HasPrefix(line, "#") && !strings.HasPrefix(line, "#_")) {
            continue
        }
        if strings.HasPrefix(line, "[") && strings.HasSuffix(line, "]") {
            currentSection = line
            continue
        }
        parts := strings.SplitN(line, "=", 2)
        if len(parts) != 2 {
            continue
        }
        key := strings.TrimSpace(parts[0])
        value := strings.TrimSpace(parts[1])

        switch {
        case currentSection == "[Interface]" && key == "PrivateKey":
            creds.PrivateKey = value
        case currentSection == "[Peer]" && key == "PresharedKey":
            creds.PresharedKey = value
        }
    }
    if err := scanner.Err(); err != nil {
        return PeerCredentials{}, fmt.Errorf("scan %s: %w", configPath, err)
    }

    // Derive PublicKey from PrivateKey if available.
    if creds.PrivateKey != "" {
        creds.PublicKey = DerivePublicKey(creds.PrivateKey)
    }

    return creds, nil
}
```

**Then extend** `LoadCredentials` to fall back to client configs when the server config is missing:

```go
func LoadCredentials(outputDir, serverPeerName string) (*PersistedCredentials, error) {
    serverConfigPath := filepath.Join(outputDir, serverPeerName, outputConfigName)

    serverCfg, err := LoadServerConfig(serverConfigPath)
    if err != nil && !os.IsNotExist(err) {
        return nil, fmt.Errorf("load server config for credentials: %w", err)
    }

    creds := EmptyCredentials()

    if err == nil {
        // Server config exists — extract from it (primary path).
        creds.Server = PeerCredentials{
            PrivateKey: serverCfg.Interface.PrivateKey,
            PublicKey:  serverCfg.Interface.PublicKey,
        }
        for _, peer := range serverCfg.Peers {
            if peer.Name == "" {
                continue
            }
            creds.Peers[peer.Name] = PeerCredentials{
                PrivateKey:   peer.PrivateKey,
                PublicKey:    peer.PublicKey,
                PresharedKey: peer.PresharedKey,
            }
        }
        return creds, nil
    }

    // Fallback: server config missing. Scan subdirectories for client configs.
    entries, dirErr := os.ReadDir(outputDir)
    if os.IsNotExist(dirErr) {
        return creds, nil // first run — no output dir at all
    }
    if dirErr != nil {
        return nil, fmt.Errorf("read output dir: %w", dirErr)
    }

    for _, entry := range entries {
        if !entry.IsDir() || entry.Name() == serverPeerName {
            continue
        }
        clientPath := filepath.Join(outputDir, entry.Name(), outputConfigName)
        peerCreds, clientErr := extractClientCredentials(clientPath)
        if clientErr != nil {
            continue // skip unreadable client configs
        }
        if peerCreds.PrivateKey != "" {
            creds.Peers[entry.Name()] = peerCreds
        }
    }

    return creds, nil
}
```

**Important correctness note**: `DerivePublicKey` in `keys.go:34-54` panics on invalid base64. In the client fallback path, we call it on values read from disk. If a user manually corrupted a config, this would panic. Consider wrapping in a recover or validating base64 first. For v1, document that corrupted configs produce panics — the generator's own output is always valid base64. If this becomes a user-facing problem, add `TryDerivePublicKey(string) (string, error)` in a follow-up.

## 7. Consumer Contract (for P2.4)

This section documents how P2.4's `Generate` pipeline will use `LoadCredentials`. Not implemented here — for reference only.

```go
// In pipeline.go (P2.4):
func Generate(manifest Manifest, opts GenerateOptions) error {
    serverPeerName := manifest.ServerPeerName() // resolved from manifest

    var creds *PersistedCredentials
    if opts.FullReset {
        creds = EmptyCredentials()
    } else {
        var err error
        creds, err = LoadCredentials(opts.OutputDir, serverPeerName)
        if err != nil {
            return fmt.Errorf("load credentials: %w", err)
        }
    }

    // Server credentials: reuse or generate.
    if creds.Server.PrivateKey == "" {
        priv, pub := GenerateKeyPair()
        creds.Server = PeerCredentials{PrivateKey: priv, PublicKey: pub}
    }

    // Per-peer credentials: reuse or generate.
    for peerName := range manifest.ClientPeers() {
        if _, exists := creds.Peers[peerName]; !exists {
            priv, pub := GenerateKeyPair()
            psk := GeneratePSK()
            creds.Peers[peerName] = PeerCredentials{
                PrivateKey: priv, PublicKey: pub, PresharedKey: psk,
            }
        }
    }

    // Build configs using creds...
    // Write atomically...
}
```

**PSK regeneration on `--full-reset`**: When `--full-reset` is set, `EmptyCredentials()` is used, so all keys AND PSKs are regenerated. This is correct because PSKs protect a specific keypair relationship — if the server key changes, PSKs should also change.

**Orphan peers**: If a peer exists in `creds.Peers` but not in the manifest, the pipeline ignores it (no output directory created). The old output directory is NOT deleted — user might want the keys for migration. P2.4 may emit a warning.

## 8. Risks and Edge Cases

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| Server config missing but client configs exist (migration scenario) | Medium | Lost server credentials, but peer credentials recovered via fallback | Fallback scanner (Step D) reads client configs from peer subdirectories. Server credentials must be regenerated — document this. |
| Peer name collision in manifest vs. output | Low | Wrong credentials loaded for wrong peer | Peer names are the primary key in both manifest and output dir names. Name uniqueness is enforced by manifest validation (P2.1). |
| Manually edited output config with corrupted base64 keys | Low | `DerivePublicKey` panics | For v1, document that manually corrupted configs are unsupported. Add `TryDerivePublicKey` in follow-up if user reports hit this. |
| `#_PrivateKey` metadata comment not present in legacy configs | Medium | Peer private keys not recovered | Only affects configs generated by non-amnezigo tools. For amnezigo-generated configs, `writer.go:76` always writes `#_PrivateKey`. Document that legacy imports require `--full-reset`. |
| `#_Name` metadata comment not present | Medium | Peer cannot be matched to manifest entry, skipped | The `peer.Name == ""` guard in Step B handles this gracefully. Unnamed peers are skipped with no error. |
| Output directory permissions (read-only) | Low | `os.Open` fails | `LoadServerConfig` returns error, which is returned to caller. Clear error message. |
| Very large number of peers (>1000) | Low | Performance | Single file read + parse. `ParseServerConfig` is O(n) in file lines. Even 10000 peers parse in <100ms. |
| Race condition: concurrent `generate` runs | Low | Config file partially written during read | P2.4 uses atomic write (write to `.tmp`, then `os.Rename`). Read either sees old complete file or new complete file, never partial. |
| `--full-reset` semantics unclear to users | Medium | User accidentally regenerates all keys | P2.4 documents `--full-reset` as "regenerate ALL keys, breaking ALL existing connections". Require `--force` confirmation if interactive. |

## 10. Out of Scope (Explicit)

The following are **deliberately excluded** from this PR:

- **`--full-reset` CLI flag**. `EmptyCredentials()` is the mechanism; the flag wiring belongs to P2.4 (`generate` command).
- **`Generate` pipeline integration**. This PR provides the credential loading layer only. P2.4 consumes it.
- **Orphan peer detection/warning**. Detecting peers in output but not in manifest is a pipeline concern (P2.4).
- **Full `ParseClientConfig`**. A lightweight extractor (`extractClientCredentials`) suffices for credential extraction. A full client parser is tracked as P1.3-followup.
- **I-packet (I1-I5) persistence**. I-packets are regenerated every run by design (fingerprint resistance). Only keypairs and PSKs are persisted.
- **Credential encryption at rest**. Keys are stored in plaintext in `.conf` files, same as standard WireGuard. OS-level file permissions are the protection layer.
- **Credential migration from other tools**. Configs from other AWG generators may use different metadata conventions. `--full-reset` is the migration path.
- **`TryDerivePublicKey` (non-panicking key derivation)**. `DerivePublicKey` panics on bad base64. Defer safe variant until a user hits this with corrupted configs.
- **Output directory deletion/cleanup**. Read-only operation. Never modifies or deletes output.

If any of these come up during implementation, **do not include them**. Note for the next PR.
