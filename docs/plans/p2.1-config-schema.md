## 1. Context

`amnezigo` is a Go CLI at `/home/arsolitt/projects/amnezigo` that generates AmneziaWG v2.0 configuration files. The current architecture is imperative: the user runs `init`, `add`, `edit`, `remove`, `export` commands sequentially. Roadmap decision 5 (`docs/roadmap.md` line 5) mandates replacing this flow with a declarative config-driven model: a single manifest file declares the full network topology, and `amnezigo generate` produces per-peer output directories.

This PR introduces the **manifest schema** — the Go struct definitions that represent the user-facing configuration format. These types are the contract between the user and the generator. Every downstream P2 item (loader, credential persistence, generate command, legacy removal) depends on this schema being stable and well-tested.

Current state:

- `types.go:10-119` defines **output types** (`ServerConfig`, `PeerConfig`, `ClientConfig`, etc.) used by the generator and writer. These represent what the generator produces — INI-format WireGuard configs.
- `presets.go:8-16` defines the `Preset` struct with all obfuscation parameters. Presets are a jsonnet-level concern; the manifest does not reference them directly.
- `generator.go:174-216` orchestrates generation via `GenerateConfig`, consuming `ServerObfuscationConfig` and `ClientObfuscationConfig`.
- No manifest types exist. No JSON-based user-facing configuration format is defined. The gap between "what the user wants to declare" and "what the generator consumes" has no typed bridge.

Reasons to ship the schema first (before loader, before generate):

1. **Contract stability**. Downstream PRs (P2.2 loader, P2.4 generate) need to import these types. Shipping types separately lets us iterate on the schema in isolation, with full test coverage, before wiring any I/O.
2. **Serialization round-trip confidence**. JSON tags, `omitempty` behavior, and validation tags must be pinned and tested before a loader writes deserialization logic against them. Discovering a tag mismatch after the loader exists is expensive.
3. **Design documentation**. The struct definitions *are* the schema documentation. Go struct tags are the canonical source; a JSON Schema file is a follow-up convenience, not the primary artifact.

## 2. Goal

Define the complete manifest schema as Go structs in a new `manifest.go` file, with comprehensive tests in `manifest_test.go`. The types must:

- Unmarshal from JSON matching the draft schema in `docs/roadmap.md` lines 401-431.
- Distinguish server peers (have `endpoint` + `listen_port`) from client peers (don't have them) programmatically.
- Support obfuscation via explicit inline parameters only (presets are handled entirely in jsonnet, user responsibility).
- Carry JSON tags on every field for clean serialization.
- Preserve peer ordering despite using a map-based API (peers as `map[string]PeerManifest`).
- Include a `version` field for forward compatibility.
- NOT touch the existing output types in `types.go` — manifest types are a separate layer.

**In scope (this PR):**

- `manifest.go` — all manifest types: `Manifest`, `NetworkConfig`, `ObfuscationManifest`, `PeerManifest`.
- `manifest_test.go` — JSON round-trip tests, validation edge cases, server-peer detection.
- Design decisions documented in this plan (peer naming, obfuscation composability, version semantics).

**Explicit out-of-scope (deferred):**

- JSON Schema file generation. Useful for editor autocomplete but not blocking; tracked as a follow-up.
- Jsonnet evaluation. That's P2.2 (loader). This PR defines Go structs; jsonnet is an input format that produces the same JSON shape.
- Manifest validation logic (`ValidateManifest`). That's P3.1. This PR defines the types; validation orchestration is a separate concern.
- Conversion from manifest types to output types (`ManifestToServerConfig`). That's P2.4 (generate pipeline).
- CLI wiring. No new commands in this PR.

## 4. Architecture Decisions

### 4.1 Manifest types live in `manifest.go`, not a new package

**Decision**: create `manifest.go` in the root `amnezigo` package alongside `types.go`.

**Rationale**:

- Manifest types need to reference `HeaderRange` (`types.go:6-8`) and will later be converted to `ServerObfuscationConfig` (`types.go:47-51`) during generation. Same-package access avoids export gymnastics.
- The `amnezigo` package is the domain layer. Both output types and manifest types are domain concepts; separating them into packages would split the domain model without clear benefit.
- When `pipeline.go` (P2.4) converts `Manifest` → `ServerConfig`, it needs both types in scope. Same package makes this natural.
- File count is manageable: `manifest.go` (~200 lines of types) + `manifest_test.go` (~350 lines of tests). The package stays well below the size that would justify extraction.
- Alternative considered: `internal/manifest/` package. Rejected: would force exporting `HeaderRange` from root package, or duplicating it. Complexity without benefit at this scale.

### 4.2 Manifest struct — top-level with `version`, `network`, `obfuscation`, `peers`

**Decision**: define `Manifest` as:

```go
type Manifest struct {
    Version      int                      `json:"version"`
    Network      NetworkConfig            `json:"network"`
    Obfuscation  ObfuscationManifest      `json:"obfuscation"`
    Peers        map[string]PeerManifest  `json:"peers"`
}
```

**Field semantics**:

- `Version` — must be `1` in v1. Loader (P2.2) and validator (P3.1) will reject unknown versions. The field exists for forward compatibility: when the schema evolves, version-aware loaders can migrate or reject cleanly.
- `Network` — global settings that apply to all peers equally (MTU, DNS). Not per-peer because AWG/WG MTU is per-interface, not per-peer (`docs/roadmap.md` line 452).
- `Obfuscation` — the obfuscation profile with explicit parameters only. Server-wide parameters (S1-S4, H1-H4, Jc/Jmin/Jmax) must match across all peers per AWG 2.0 spec (`docs/roadmap.md` line 19). Per-peer I-packets are NOT in the manifest — they are generated per-run by the pipeline. Presets are NOT in the manifest — they are a jsonnet-level concern (users compose obfuscation values in jsonnet using presets, and the resulting JSON contains only resolved values).
- `Peers` — all network participants. Map key is the peer name (used as output directory name and for human reference). Server and client peers are distinguished by the presence of `Endpoint` + `ListenPort` fields.

**Rationale**:

- Flat structure mirrors the roadmap draft (`docs/roadmap.md:401-431`). No nesting beyond one level.
- `map[string]PeerManifest` matches the roadmap's jsonnet example where peers are object keys (`server:`, `phone:`, `laptop:`). The map key IS the peer name — no separate `name` field inside `PeerManifest`.
- Version as integer (not string) keeps comparison simple (`if m.Version != 1`) and matches common practice (Kubernetes API version numbers, Compose file version).

### 4.3 Peer ordering — `map[string]PeerManifest` with deterministic output, no ordered-map library

**Decision**: use plain `map[string]PeerManifest` for the peers field. When deterministic iteration order is needed (output directory creation, config file generation), sort the keys alphabetically. Do NOT add an ordered-map dependency.

**Rationale**:

- The roadmap mentions "use `map[string]PeerManifest` with a separate `[]string` for ordered keys, or an ordered-map library" (`docs/roadmap.md:442`). However, neither approach is needed for v1:
  - **Sorted keys** give deterministic output across runs. The user's JSON source order is not meaningful — what matters is that `generate` produces the same output given the same input.
  - **Insertion-order preservation** would only matter if the user expected output directories to appear in source order. They don't — output is filesystem-based, and filesystems don't preserve creation order visually.
  - An ordered-map library adds a dependency to `go.mod` for a property that has no user-facing effect.
- The `[]string` companion slice approach works but adds complexity to every consumer (must iterate the slice, look up each key in the map, handle missing-key errors). Sorted keys is simpler.
- If a future requirement emerges (e.g., "peers should appear in config order for diff stability"), we can add a `PeerOrder []string` field to `Manifest` without breaking the JSON shape (new optional field, `omitempty`). That's a one-commit change, not a rearchitecture.
- Testing approach: round-trip tests compare the marshaled JSON after sorting keys, ensuring deterministic output regardless of Go's map iteration order.

### 4.4 Server vs client peer distinction — structural, not via a `role` field

**Decision**: a peer is a "server peer" if and only if it has a non-empty `Endpoint` AND a non-zero `ListenPort`. All other peers are "client peers". There is no explicit `role` or `type` field.

**Rationale**:

- The roadmap states: "Server peer (the one with `endpoint` + `listen_port`) is identifiable programmatically — at most one peer may have `endpoint` set" (`docs/roadmap.md:444`).
- Structural detection avoids redundancy. If we added a `role: "server"` field, users could misconfigure it (set `role: server` without an endpoint, or set endpoint without `role: server`). Structural detection has one source of truth.
- Helper method `(PeerManifest) IsServer() bool` makes the check explicit and self-documenting in consuming code.
- Validation (P3.1) will enforce: exactly one peer is a server peer. Zero or more-than-one is an error. This PR does not implement validation — it provides the `IsServer()` predicate that validation will call.

**Server-only fields**:

- `Endpoint` — the public address clients connect to (e.g., `vpn.example.com:51820`). Only server peers have this.
- `ListenPort` — the UDP port the server listens on. Only server peers have this.
- `MainIface` — the main network interface name (e.g., `eth0`). Only relevant for server peers. Used to auto-generate iptables `PostUp`/`PostDown` rules during generation. Empty/ignored for client peers.

**Fields applicable to both roles**:

- `TunName` — WireGuard tunnel interface name. Defaults to `"awg0"`. Used by both server and client peers for the `[Interface]` section of the generated config.

**Client-only fields**:

- None that are schema-exclusive. Clients simply omit `Endpoint` and `ListenPort`. Every other field (address, protocol override, keepalive) applies to both roles.

**Subnet mask validation**:

Client peer addresses MUST use host masks: `/32` for IPv4 or `/128` for IPv6. The server peer may use a broader mask (e.g., `/24`) for its own address since it represents the network's gateway. Validation (P3.1) will enforce this via rule `MNF010` — non-server peers with non-host masks produce an error finding. This ensures each client has a unique, unambiguous IP address within the server's subnet.

### 4.5 Obfuscation — explicit params only, presets are a jsonnet concern

**Decision**: `ObfuscationManifest` carries only explicit obfuscation parameters. There is NO `preset` field. Presets are handled entirely at the jsonnet level — users compose obfuscation values in jsonnet using preset functions, and the resulting JSON contains only resolved numeric values.

```go
type ObfuscationManifest struct {
    Protocol string       `json:"protocol,omitempty"`
    S1       *int         `json:"s1,omitempty"`
    S2       *int         `json:"s2,omitempty"`
    S3       *int         `json:"s3,omitempty"`
    S4       *int         `json:"s4,omitempty"`
    H1       *HeaderRange `json:"h1,omitempty"`
    H2       *HeaderRange `json:"h2,omitempty"`
    H3       *HeaderRange `json:"h3,omitempty"`
    H4       *HeaderRange `json:"h4,omitempty"`
    Jc       *int         `json:"jc,omitempty"`
    Jmin     *int         `json:"jmin,omitempty"`
    Jmax     *int         `json:"jmax,omitempty"`
}
```

**Pointer types for explicit params**:

- `*int` and `*HeaderRange` distinguish "user set this to 0" from "user didn't set this". Without pointers, `S1: 0` and `S1: <absent>` are indistinguishable after unmarshaling.
- `omitempty` on pointer fields means `null` / absent fields produce a zero pointer, which `json.Marshal` omits on round-trip. This keeps the JSON clean: only the fields the user set appear in the output.

**Why no preset field**:

- Presets are a jsonnet-level abstraction. The user writes `obfuscation: presets.homeBalanced` in their jsonnet file, and jsonnet resolves it to explicit values before producing JSON. The manifest schema only sees the resolved result.
- This eliminates the need for preset-vs-explicit mutual-exclusivity validation, the `HasExplicitParams()` helper, and the `Preset` field entirely. Simpler schema, simpler validation.
- The `GetPreset()` function from `presets.go` may still be used by jsonnet tooling or documentation, but the manifest types are agnostic to it.

**HeaderRange JSON serialization**:

- `HeaderRange` (`types.go:6-8`) currently has no JSON tags. This PR adds JSON tags to enable serialization within the manifest context. The range serializes as `"h1": {"min": 100, "max": 5000000}` matching the Go struct shape.
- Alternative considered: string form `"h1": "100-5000000"` matching the INI parser's `min-max` notation. Rejected: introduces parsing complexity (the loader must split strings and validate numeric ranges) when the struct-native JSON form is unambiguous and machine-friendly. Jsonnet users can write `h1: { min: 100, max: 5000000 }` naturally.

**Protocol field**:

- `Protocol` is the default I-packet protocol for all peers. Per-peer overrides exist in `PeerManifest.Protocol`. If neither is set, the generator uses `"random"` (existing default from `protocols.go`).
- This field is on `ObfuscationManifest`, not on `Manifest`, because it controls I-packet shape, which is part of the obfuscation profile. Conceptually it belongs with S/H/J params.

### 4.6 PeerManifest — flat struct with role-dependent fields

**Decision**:

```go
type PeerManifest struct {
    Address    string `json:"address"`
    TunName    string `json:"tun_name,omitempty"`
    MainIface  string `json:"main_iface,omitempty"`
    Endpoint   string `json:"endpoint,omitempty"`
    Protocol   string `json:"protocol,omitempty"`
    ListenPort int    `json:"listen_port,omitempty"`
    Keepalive  *int   `json:"keepalive,omitempty"`
}
```

**Field semantics**:

- `Address` — WireGuard interface address in CIDR notation (e.g., `10.0.0.1/24` for server, `10.0.0.2/32` for client). Required for all peers. The roadmap asks if addresses should be auto-assigned (`docs/roadmap.md:451`); answer: **explicit CIDR for all peers**. Auto-assignment is magic that hides network topology; a declarative config should declare, not infer.
- `TunName` — WireGuard tunnel interface name (e.g., `awg0`). Defaults to `"awg0"` when empty. Used in the generated config's `[Interface]` section. Applies to both server and client peers.
- `MainIface` — the main network interface name (e.g., `eth0`). Only relevant for server peers. When set, the generator auto-generates iptables `PostUp`/`PostDown` rules for NAT forwarding. Empty or absent for client peers (ignored). This replaces manual PostUp/PostDown string fields — the generator derives iptables rules from `TunName` + `MainIface` automatically.
- `Endpoint` — server's public address as `host:port` string. Only server peers set this. Used by client configs' `[Peer] Endpoint = ...` line.
- `ListenPort` — UDP listen port. Only server peers set this. Used in the server config's `[Interface] ListenPort = ...` line.
- `Protocol` — per-peer I-packet protocol override. Overrides `ObfuscationManifest.Protocol` for this peer. When empty, inherits the global default.
- `Keepalive` — WireGuard `PersistentKeepalive` interval in seconds. Uses `*int` pointer type to distinguish "not set" (nil, default to 20) from "explicitly set to 0" (disabled). When nil, the generator applies a default of 20 seconds. When explicitly `0`, keepalive is disabled (no `PersistentKeepalive` line in output). The `omitempty` tag ensures nil pointers are omitted from JSON output.

**What PeerManifest does NOT contain**:

- **Name**: the map key in `Manifest.Peers` IS the name. No duplication.
- **Keys (PrivateKey, PublicKey, PresharedKey)**: credentials are not part of the user-facing manifest. They are generated and persisted by the credential layer (P2.3). The manifest declares topology, not secrets.
- **AllowedIPs**: derived from the network topology by the generator. Server peer gets all client addresses; client peers get `0.0.0.0/0` (or configurable). Not user-facing in v1.
- **DNS**: global, lives in `NetworkConfig`, not per-peer. WireGuard DNS is per-interface on the client, but all clients in one manifest share the same DNS config.
- **I-packets (I1-I5)**: generated per-run, not declared. The manifest specifies the protocol template; the generator produces the actual CPS strings.
- **PostUp / PostDown**: auto-generated from `TunName` and `MainIface` fields. The user no longer writes raw iptables strings — the generator derives them.

### 4.7 NetworkConfig — MTU and DNS

**Decision**:

```go
type NetworkConfig struct {
    DNS []string `json:"dns,omitempty"`
    MTU int      `json:"mtu,omitempty"`
}
```

**Field semantics**:

- `MTU` — WireGuard interface MTU. When `0` / absent, the generator uses its default (`1280` — see `generator.go` and preset defaults at `presets.go:13`). Global because AWG/WG MTU is per-interface, all peers on the same network use the same MTU.
- `DNS` — DNS servers for client configs' `[Interface] DNS = ...` line. String slice for multiple servers. Server peer ignores this (server's DNS is system-configured, not WG-managed). When empty, no `DNS` line is written to client configs.

**What NetworkConfig does NOT contain**:

- **Subnet / address pool**: addresses are explicit per-peer, not auto-assigned.
- **Interface name**: lives on `PeerManifest.TunName` (per-peer tunnel interface name, defaults to `"awg0"`).

### 4.8 HeaderRange JSON tags — add to existing type

**Decision**: add JSON tags to the existing `HeaderRange` struct in `types.go`:

```go
type HeaderRange struct {
    Min uint32 `json:"min"`
    Max uint32 `json:"max"`
}
```

**Rationale**:

- `HeaderRange` is shared between output types and manifest types. Adding JSON tags makes it serializable for the manifest without duplicating the type.
- The output layer (`writer.go`) serializes to INI format, not JSON. Adding JSON tags does not affect INI serialization — `writer.go` accesses `.Min` and `.Max` directly, ignoring tags.
- JSON tags use lowercase (`min`, `max`) matching Go JSON convention and the roadmap's jsonnet example style.

### 4.9 Version field — integer, validated at load time

**Decision**: `Version` is `int`, not `string`. v1 is `1`. Validation (P3.1) and loader (P2.2) will reject any value other than `1`.

**Rationale**:

- Integer comparison is simpler than string comparison or semver parsing.
- Kubernetes API versioning (e.g., `v1`, `v1beta1`) uses strings, but that's for multi-track evolution. We have one track.
- If a future schema needs breaking changes, `Version: 2` with a migration function is the upgrade path. The version field is the discriminator.
- The manifest types do NOT enforce version at the type level — that's validation/loader logic. The struct just stores it.

// a field in this struct.

// Manifest is the top-level user-facing configuration format for amnezigo.
// It declares the full network topology: global settings, obfuscation
// profile, and all peers in a flat map. The manifest replaces the old
// imperative init/add/edit/remove/export flow with a single declarative
// file that drives `amnezigo generate`.
//
// Version must be 1. The version field exists for forward compatibility;
// future schema changes bump the version and may include migration logic.
//
// Peer names are map keys in the Peers field. The name is used as the
// output directory name and for human reference. Keys must be unique
// (enforced by JSON/map semantics) and should avoid reserved names.
type Manifest struct {
    Network     NetworkConfig              `json:"network"`
    Obfuscation ObfuscationManifest        `json:"obfuscation"`
    Peers       map[string]PeerManifest    `json:"peers"`
    Version     int                        `json:"version"`
}

// ServerPeer returns the name and count of server peers in the manifest.
// A valid manifest has exactly one server peer (count == 1). If count is
// 0 or > 1, validation should reject the manifest.
//
// When count > 1, the returned name is one of the server peers (arbitrary
// due to map iteration order) — callers should check count first.
func (m *Manifest) ServerPeer() (name string, count int) {
    for n, p := range m.Peers {
        if p.IsServer() {
            name = n
            count++
        }
    }
    return name, count
}

// ServerPeerName returns the name of the sole server peer. It panics if
// the manifest does not contain exactly one server peer. Use this in
// code paths that have already validated the manifest (e.g., the generate
// pipeline). Use ServerPeer() for validation code that needs the count.
func (m *Manifest) ServerPeerName() string {
    name, count := m.ServerPeer()
    if count != 1 {
        panic(fmt.Sprintf("ServerPeerName: expected exactly 1 server peer, found %d", count))
    }
    return name
}

// PeerNames returns all peer names sorted alphabetically. Use this when
// deterministic iteration order is needed (output directory creation,
// config file generation, testing).
func (m *Manifest) PeerNames() []string {
    names := make([]string, 0, len(m.Peers))
    for n := range m.Peers {
        names = append(names, n)
    }
    sort.Strings(names)
    return names
}

## 8. Relationship to Existing Types

This diagram clarifies the boundary between manifest types (user-facing, JSON) and output types (generator-internal, INI):

```text
User writes:                  Generator converts:              Writer outputs:
-----------                   --------------------             ---------------
Manifest                      ┌─────────────────┐
  .Network        ──────────> │  pipeline.go     │ ──────────> ServerConfig (INI)
  .Obfuscation    ──────────> │  (P2.4)          │               .Interface
  .Peers["server"]──────────> │                  │               .Peers[]
  .Peers["phone"] ──────────> │  generates keys  │               .Obfuscation
                              │  builds CPS      │
                              │  builds CPS      │ ──────────> ClientConfig (INI)
                              │  validates       │               per peer
                              └─────────────────┘

Manifest types (this PR):     Conversion (P2.4):               Output types (existing):
  manifest.go                   pipeline.go                      types.go
  - Manifest                    - ManifestToServerConfig()       - ServerConfig
  - NetworkConfig               - ManifestToClientConfig()       - ClientConfig
  - ObfuscationManifest                                          - InterfaceConfig
  - PeerManifest                                                 - PeerConfig
                                                                 - ServerObfuscationConfig
                                                                 - ClientObfuscationConfig
```

**Key design principle**: manifest types and output types are distinct layers. The manifest declares *intent* (what the user wants); the output types represent *result* (what the generator produces). The conversion layer (P2.4) bridges them. This PR does NOT implement conversion — it only defines the intent layer.

## 9. Risks and Edge Cases

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| JSON tag name collides with future Go field name after casing | Low | Refactoring pain | All JSON tags are lowercase snake_case; Go fields are PascalCase. No collision vector. |
| `HeaderRange` JSON tags break existing serialization | None | n/a | `HeaderRange` is currently serialized only via `writer.go` INI format, which accesses `.Min`/`.Max` directly. JSON tags are additive, not breaking. Verified by reading `writer.go`. |
| Pointer types for `ObfuscationManifest` fields complicate consumer code | Medium | Verbosity | Future helpers can extract resolved values (pointer dereference with defaults). Verbosity is acceptable for the nil-vs-zero correctness gained. |
| Map-based peers lose insertion order from JSON source | Medium | User surprise if output order differs from source | Documented in section 4.3. `PeerNames()` returns sorted names for deterministic output. If order matters to users, add `PeerOrder []string` later (non-breaking). |
| Peer name collides with reserved filesystem names (`output`, `.git`, `..`) | Medium | Output directory creation fails | Validation (P3.1) will reject reserved names. This PR provides the types; validation is downstream. Document reserved names in struct comments. |
| `version: 0` or absent version field silently accepted | Low | Forward compat violation | `Version` has no `omitempty` tag, so it's always present in marshaled output. Absent in input → defaults to `0` (Go zero value). Validation (P3.1) will reject `!= 1`. |
| Schema evolution needs field additions | Expected | Must not break existing manifests | All new fields in future versions use `omitempty`. Existing manifests unmarshal cleanly into newer struct versions (unknown fields are ignored by default `json.Unmarshal`). Tested by `TestManifest_UnmarshalExtraFields`. |
| `PeerManifest.Address` with invalid CIDR notation | Medium | Runtime error during generation | This PR does not validate CIDR format — that's P3.1 (validation). The type stores the raw string. |

## 12. Out of Scope (Explicit)

The following are **deliberately excluded** from this PR:

- **JSON Schema file generation**. Useful for editor autocomplete but not blocking for downstream P2 items. Can be added as a follow-up.
- **Jsonnet evaluation**. That's P2.2 (loader). Manifest types are the Go structs; jsonnet is an input format that produces the same JSON.
- **Manifest validation logic** (`ValidateManifest`). That's P3.1. This PR defines types; validation is a separate concern.
- **Conversion to output types** (`ManifestToServerConfig`). That's P2.4 (generate pipeline). This PR defines the source layer; conversion is downstream.
- **CLI wiring**. No new commands in this PR. `generate` is P2.4.
- **Credential fields in PeerManifest**. Keys are generated and persisted by P2.3. The manifest declares topology, not secrets.
- **AllowedIPs in PeerManifest**. Derived from topology by the generator, not declared by the user.
- **Per-peer MTU or DNS**. AWG MTU is per-interface; DNS is global. Documented in section 4.7.
- **Ordered-map dependency for peer ordering**. Sorted keys are sufficient (section 4.3).
- **Preset field in ObfuscationManifest**. Presets are resolved at the jsonnet level; the manifest carries only explicit values.

If any of these come up during implementation, **do not include them**. Note for the next PR.
